## B0-1 卡片 worker 竞态（连点出两个 worker、停止后旧卡续跑）

**根因**：`SHOW_STOP` 是全局 Event。新 worker 开头 `clear()` 会把"停止旧卡片"刚 `set()` 的信号吃掉 → 连点两次起两个 worker 同驱一张卡；停止 A 再开 B，A 收不到停止信号继续把通道推往 A 的目标。

**改动点**：
- 删除全局 `SHOW_STOP`，改为按次运行的"代"机制：`SHOW_RUN = {gen, stop, card}`，每次启动发新代号 + 专属停止 Event（`run_show` / `_show_worker` / `_run_card_on_timeline` 全链路带 `run_ev, gen`）
- 旧 worker 只认自己那代的 Event，物理上不可能被新运行清掉；共享状态（`SHOW_STATE`）退场清理带代号校验，旧代退场不擦新代状态
- `run_show` 返回是否启动（连点同一张卡直接忽略，返 `already:true`）；`clear_console`、一键撤销、`/api/show` 停止/启动全部改走新机制（`_show_stop_current`）

**影响范围**：卡片启动/停止/接续链、空台子、一键撤销；不动时间轴插值与动作语义。

**潜在风险与审查**：
- 链条接续（`next` 字段）与防环逻辑未动，专门验证：跑完后再点同一张卡能正常重启；`next` 链两卡顺序执行；中途停止后**不接续**下一张（日志确认无"接续"记录）
- 并发场景复测走查用例 3/3 通过；presets 组 15/15 无回归

## B0-2 桥接转发用入参原始值（本地 1.0 / 真台 1.7、NaN 照发）

**根因**：`_bridge_forward` 收的是调用入参——本地把 1.7 钳到 1.000，真台却收到 1.7；`"nan"` 也顺着 OSC 发往真台。

**改动点**：
- `set_value` 转发点改为 `get_value(kind, idx)`（写进 STATE 之后、钳制/消毒后的值）；`get_value` 返回 None（本地无此目标）不转发
- `_bridge_forward` 增加第二道闸：`math.isfinite` 不通过直接拒发并记日志

**影响范围**：所有桥接转发路径（manual/action/dca/fade 四类来源）。

**潜在风险与审查**：
- 回声抑制（`FWD_RECENT`）登记的仍是实际发出的值，一致性未破坏
- 假真台实测：本地钳到 1.000 时真台收到 1.0（一致）；NaN 输入转发 0 包；bridge 组 18/18 无回归

## B0-3 持久化三种"假成功"（非原子写 / 坏文件静默清空 / 不可写仍返 ok）

**根因**：直接开文件写（断电出半文件）；坏 JSON 只 log 一声然后用默认配置继续（预设/卡片静默全丢）；目录不可写时 `save_user_config` 吞异常，HTTP 层照返 200 `ok:true`。

**改动点**：
- `save_user_config`：加 `CONFIG_SAVE_LOCK` 串行化 + 写临时文件 + `os.replace` **原子替换**，返回值改为 bool；`allow_nan=False` 兜底
- 坏配置文件：备份为 `<文件>.corrupt-<时间戳>`（备份失败则原文件不动），明确日志告知用户"修复后可并回"，本次用默认配置启动
- HTTP 层新增 `_cfg_saved()`：写盘失败返 **500 + 错误原因**，不再假成功；14 处保存点全部接线，并补齐了原本只改内存不落盘的点（fx 参数、FX 同步、ports、names、keycfg、keyadd/keydel/keyedit、cardadd/cardedit/cardpin/carddel、snapshot delete）
- 前端 `api()` 原是 fire-and-forget（500 用户看不见）→ 失败弹 toast

**影响范围**：所有写配置的接口、启动加载路径、前端错误可见性。

**潜在风险与审查**：
- 原子替换在 Windows 上偶发"目标被占用"的瞬间拒绝（实测 486 次并发读取仅 1 次打开被拒，**无一读到半文件**）；已在锁内重试一次
- 坏 scope 预设被跳过时，启动迁移**不自动保存**（避免把用户待修的数据抹掉），旧结构留内存不影响运行
- 实测：并发 60 次保存期间读文件 0 次损坏；删除预设/keycfg 均落盘；重启后不复活

## B0-4 非法预设 scope 静默回落全量（局部变全局）

**根因**：`clean_preset_scope` 对脏输入一律"规范化"成默认全量（158 值）——用户以为存了局部，回归时误改全台。

**改动点**：
- `clean_preset_scope` 改为**明确拒绝**：非 dict / 空 groups / params 与 groups 无交集 / indices 编号全越界 → 抛 `ValueError`
- `save_snapshot` 返回 `(snap, saved_ok)`；`/api/snapshot` save 捕获 `ValueError` → **400 + 原因**，内存里也不留这条预设
- `load_user_config`：scope 非法的预设**跳过并记日志**，但保留在文件里等用户修（不再静默清空全部预设）；日志明示"N 条因范围非法被跳过"

**影响范围**：预设保存/加载/回归；合法 scope 行为不变。

**潜在风险与审查**：
- 与 B0-3 的坏文件备份策略叠加验证：手改坏 scope 预设 + 一条好预设 → 重启后只载入好的，坏的原样留在文件里，配置文件不被启动流程改动
- 6 个非法/合法组合实测全部符合预期；presets 组无回归

## B0-5 桥接写风暴（fade 期 900–1000 包/秒）

**根因**：每条写入单独 `sendto`，80 个地址 × 20Hz ≈ 1000+ UDP 包/秒，真台 OSC 栈被刷满。

**改动点（主体）**：
- 新增转发合并器：高频写入进 `BRIDGE_FWD["pending"]`（同地址只留最新值），常驻线程每 20ms 把到期条目打成一个 **Bundle** 发出
- 按来源分档限速：手动 50ms（保拖拽灵敏）/ 渐变与动作 250ms（真台 4Hz 跟随电动推子无感知）/ DCA 100ms；单拍上限 256 条防爆包
- 合并器外壳任何异常自动重启并记日志（静默死亡 = 转发永远停）；启动点幂等，`--bridge` 参数路径也覆盖
- **终值保证**：pending 始终只留最新值，渐变到点/停止后一拍内必发出（实测终值 float32 精度送达）

**审查中发现并当场修复的 3 个衍生缺陷**：

1. **停止时冻结值不同步**（合并器引入）：卡片/回归中途停止后，最后一次插值可能还压在 pending 或被限速挡下 → 真台停在中间值，与本地冻结值差一个 tick（短渐变可达 ~0.6dB）。
   修复：`_bridge_force_sync()` 在停止时把驱动目标的**当前本地值**强制转发（`force` 绕过限速，gap=0）；卡片停止同步 `FADE_ZONE`（跳过已接管通道），回归停止同步 `RECALL_ZONE`。实测本地与真台差 0.00000。

2. **回归打断竞态**（与 B0-1 同族，既有缺陷）：`RECALL_STOP` 全局 Event + 新回归 worker 开头 `clear()` → 旧回归的坡道收不到停止信号，和新回归抢同一批通道，谁后跑完谁说话。
   修复：`RECALL_GEN` 代号机制（启动/停止都发新代号，旧 worker 下次检查即退场）；`RECALL_ZONE` 带代号登记/清理，旧代退场不擦新代。实测 A(4s→0.5) 进行中启动 B(1s→0.9)，终值正确等于 B 目标 0.9。

3. **积压渐变值覆盖手动接管**（合并器引入，最严重）：渐变值在 pending 里还没发出时，真台手动干预到达 → 合并器随后把**过时的渐变值**发给真台，真台被拽回旧位并回读，回声抑制逻辑又如实应用到本地，用户的接管值被覆盖（官方 bridge 组 D 场景实测失败）。
   修复：新增 `source="fade"` 区分"渐变插值"与"显式动作"（`set`/`mute`/回归等语义是"其余动作继续"，不受接管影响）；插值在**入口**（目标已接管则拒收）和**发送时**（积压条目直接丢弃）双重拦截；`force_sync` 跳过接管通道。双模拟器端到端实测：干预后真台 ch5 稳定 0.1500、遥控/真台双边一致、ch6 继续渐变、再等 2s 无迟到包。

**影响范围**：桥接转发全链路、卡片/回归停止路径、`source` 语义（新增 fade 档）。

**潜在风险与审查**：
- 限速档位是"每地址"概念，包量降一个量级的同时单地址仍是 4Hz——与 X32-Edit 同级，真台电动推子跟随无感知
- 溢出分支（>256 条）改为"全发但仍过滤接管项"，不再无差别清空
- 指标：预设回归 912–1063 → **116 包/秒**；卡片渐变 → **273 包/秒**；手动连续写入实测 16Hz（50ms 档 + 20ms tick）
- 回归：修复期间 bridge 组曾 FAIL（上述缺陷 3），修复后全量 **6/6 全绿**

## 仍需关注的遗留事项

1. **`/api/state` 轮询流量**（P1，未在 B0 范围）：空台 14.8KB、用一阵 21.3KB，250ms 轮询 ≈ 271–300MB/h（4G 场景）。建议后续做增量推送或降频，属模块化 B5 的议题
2. **渐变期 900–1000 包/s 的本地广播面**：桥接侧已治，`MAIN_SOCK` 本地订阅广播仍是全量高频，可评估合并
3. **十项通道参数建模**（增益/反相/延时/低通/门/压缩/EQ/插入/发送/Pre-Post）：全部未建模，每项需补 8 层（地址映射/UI/钳制/STATE/推送/桥接/预设范围/回归）。按既定次序建议先做增益、反相、延时、低通、插入 5 项；发送 512 条是大工程，需单独排期
4. **模块化（B1–B5）**：本次严格限定在 B0，未动包结构；`x32sim/` 包 + 合成单文件的方案见《模块化搭建方案-v1.md》，仍待排板
5. **浮点精度说明**：OSC 是 float32，本地 float64，桥接两侧会有 ~1e-7 的固有误差（实测差值 0.00000 量级可见），非缺陷
