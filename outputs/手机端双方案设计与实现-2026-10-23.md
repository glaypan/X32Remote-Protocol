# 手机端双方案设计与实现

> 日期：2026-10-23 · 对应服务端规范 **v1.7**（tag `spec-v1.7`）
> 状态：**两种方案均已可用**；本轮补齐方案 B 的「扫码进入」环节（此前只能手输 IP）
> 关联文档：`X32Simulator/手机端方案对比分析.md`（2026-09-25，卡片引擎归属的可行性分析）

---

## 0. 一页结论

| | **方案 A · 独立 App** | **方案 B · 电脑端服务 + 网页** |
|---|---|---|
| 形态 | iOS / Android 原生应用，直连调音台 | 电脑跑 Python 服务，手机开网页 |
| 链路 | 手机 ──UDP/OSC──> 调音台 | 手机 ──HTTP──> 电脑 ──UDP/OSC──> 调音台 |
| 适用 | 只要遥控、现场不想摆电脑；Android 可常驻 | 需要卡片自动化 / 桥接 / 完整参数面板；有电脑在场 |
| 离线 | **可在无电脑的局域网内独立工作** | 必须有一台电脑在跑服务 |
| 功能上限 | 受 App 已实现范围限制（见 §2.2） | 服务端全部能力（见 §3.2） |
| 连接 | 自动发现或手输 IP，一次填好长期有效 | **扫码或输地址**，换设备零配置 |
| 更新 | 重装 App（iOS 免费证书 7 天重签） | 刷新页面即最新 |
| 安全边界 | 局域网信任 + 签名安装 | 局域网信任 + CSP/输入消毒，**无鉴权** |

一句话选型：**演出要跑卡片、要桥接真台 → 方案 B；只想拿手机当遥控器、现场不放电脑 → 方案 A。**

## 1. 一条硬约束决定了两种方案的分工

**浏览器不能发 UDP。** 网页只有 HTTP/WebSocket/WebRTC，发不出 OSC 包。所以：

> **卡片引擎（时间轴、渐变、冲突接管）跑在哪台设备上，自动化能力就只能在哪台设备上存在。**

- 引擎在电脑 → 必须有一台电脑在链路里 → **方案 B**
- 想在手机上跑引擎 → 手机里必须有能发 UDP 的原生进程 → **方案 A**

这条约束不是取舍偏好，是协议事实；它解释了为什么两种方案不能互相替代，也解释了
为什么方案 B 的网页版**必须**有电脑（`--bridge` 由电脑代发）。

## 2. 方案 A：独立安装的移动端应用

### 2.1 适用场景

| 场景 | 说明 |
|---|---|
| 现场只带手机 | 调音台在台上，人不方便回电脑前 |
| 乐队/歌手耳返微调 | 控制键按步长 ±3 dB 渐变，不误触 |
| 多手机同时用 | 每台手机各连各的，互不依赖 |
| 断网/无电脑 | 只要手机和台子在同一局域网即可 |

### 2.2 功能范围（已实现 / 未实现，必须分清）

| 能力 | iOS | Android | 说明 |
|---|---|---|---|
| 推子 / 静音 / DCA / 场景 | ✅ | ✅ | 主操作路径 |
| 卡片执行（12 种动作） | ✅ | ✅ | 白名单 12 种，**不含** `set` / `osc` / `preset` / 场景局部 recall |
| 自动发现调音台 | ✅ | ✅ | 服务端侧 UDP 广播应答（`scan.py`）已实现并有回归 |
| 通道命名 / 控制键 / 电平表 | ✅ | ✅ | |
| **75 项通道参数面板** | ❌ | ❌ | 仅网页/macOS 壳有；规范 v1.7 已标注待迁移 |
| **离线演示模式** | ❌ | ❌ | 只有 macOS 桌面版内置了模拟器 |

> 这张表是"诚实边界"：方案 A 覆盖的是**演出操作**，不是**调音台全部参数**。
> 需要逐项调门限/EQ/发送时，用方案 B 的网页面板。

### 2.3 交互方式

- 一屏一任务：底部四个页签（卡片 / 混响 / 控制键 / 调音台），不堆二级菜单
- **卡片即按钮**：点一下执行、再点停止；含「全体」类动作的危险卡**长按 0.8 秒**
- 推子：拖动即写入（不是草稿）；数值可点开键盘精调；双击回 0 dB
- 双读：百分比 + dB 同时显示（`0.0% (-∞)`），避免"看起来有值其实静音"
- 危险动作二次确认只给"全域影响"的操作，单通道操作不做拦截（现场要快）

### 2.4 连接流程

```
启动 App → 扫描（UDP 广播，3 秒）
        ├─ 发现一台或多台 → 选一台 → 连上（记住 MAC/IP）
        └─ 没发现 → 手输 IP（+ 端口，默认 10023）→ 校验（读 /info）→ 连上
连上后：/xremote 每 30 秒内续期一次，维持推送订阅
```

- 扫描失败不等于台子有问题：**AP 隔离、随机 MAC、手机热点**都会让广播收不到，
  此时手输 IP 一定能连（广播只是便利功能）
- 连接信息本地持久化，下次打开直接重连

### 2.5 稳定性与安全

| 问题 | 措施 |
|---|---|
| UDP 无连接、会丢包 | 关键写入后回读校验；`/xremote` 30 秒续期；断线红点 + 自动重连 |
| 退后台被系统挂起 | iOS 约 30 秒挂起 → 只能当前台遥控器；Android 可加电池白名单常驻 |
| 证书 7 天过期 | Sideloadly 重签，数据不丢（§`iOS-真机直装指南.md`） |
| 局域网内谁都能控 | 这是 OSC 的固有模型（真台也一样）；缓解：不把 10023 暴露到公网、演出前确认连接列表 |

## 3. 方案 B：电脑端服务 + 手机网页

### 3.1 适用场景

| 场景 | 说明 |
|---|---|
| 演出卡片自动化 | 卡片引擎在电脑上跑，渐变/并行/等待/冲突接管全都有 |
| 桥接真台 | 电脑接真台（`--bridge`），手机通过网页间接控制，电脑负责合并写风暴 |
| 逐项调参 | 75 项通道参数（门/动态/EQ/发送）只有网页有面板 |
| 临时借用设备 | 别人的手机、平板，扫码即用，不装任何东西 |

### 3.2 功能范围

服务端全部能力，没有裁剪：

- **卡片**：15 种动作（含 `set` / `osc` / `preset` / 场景全局与局部 recall）、
  时间轴 0.05 s 精度、4 种曲线、冲突只冻结被碰那一路、卡片链防环
- **参数**：75 项（前置 7 / 插入 3 / 门 11 / 动态 18 / EQ 17 / 发送 3×16 Bus）
- **预设**：可选范围快照（`scope`）+ 8 条上限 + 场景全局/局部
- **其它**：FX 槽与效果库、电平表、OSC 日志、配置导入导出、控台驱动切换

### 3.3 交互方式

- 单页 PWA（`WEB_PAGE` 一个自包含 HTML，css/js 内联），可「添加到主屏幕」全屏使用
- 五个页签：卡片 / 混响 / 控制键 / 调音台 / 设置
- 手机优先：44 px 触控目标、横向滚动的推子行、危险动作长按
- 数值可键盘精调（对数滑块 + 点数值输入），不受手指精度限制

### 3.4 连接流程（本轮补齐扫码）

```
电脑：python x32_simulator.py
      ├─ 终端打印本地地址 + 二维码（--no-qr 可关）
      └─ 网页设置页「手机 / 安卓平板连接」卡片里也有二维码
手机：扫一扫 → 直接打开 http://<电脑IP>:8080/
      或 手输地址 → 同一页面
```

三种取址顺序（`/qr.svg`）：**`?u=` 显式传参 → 请求的 Host（从手机访问时天然正确）→ 探测到的局域网 IP**。
页面显示的地址与二维码编码的内容**始终是同一个字符串**（所见即所得）。

### 3.5 稳定性与安全

| 问题 | 措施 |
|---|---|
| 4G / 弱网流量 | `/api/state?v=<指纹>` 条件轮询（无变化只回 ~30 B）、gzip、电平 0.1 dB、后台降频 2 s；实测 22.5 → 11.7 MB/h |
| 断线 | 红点 + `finally` 定时重试；不重试会造成"界面冻在上一秒"的假象 |
| 写风暴 | 电脑端 `BRIDGE_FWD` 合并器（manual 50 ms / fade·action 250 ms / DCA 100 ms） |
| XSS | 全站 `esc()` + CSP（`default-src 'self'`，禁 `object-src`/`frame-ancestors`） |
| 畸形输入 | API 入口校验 + 400 显式报错（不静默断链）、8 MB body 上限、NaN 双闸 |
| 二维码被滥用 | `/qr.svg` 只渲染**地址**、不主动请求它（无 SSRF）；非 `http(s)` 或超 200 字节直接 400 |
| 鉴权 | **未做**。同网段任何人可控制——与真台 OSC 同级的信任模型。需要时见 §7 |

## 4. 共用模块与差异点

### 4.1 共用（同一份"语义"，两种"传输"）

| 共用层 | 内容 | 落在哪 |
|---|---|---|
| 协议语义 | 75 项参数登记表（地址/量程/档位/线上类型） | `x32sim/params.py` |
| 数值换算 | dB 4 段伪对数、161 档量化、枚举双形式（索引/字符串） | `params.py`（单一实现） |
| 卡片模型 | 15 种动作、时间轴、曲线、冲突接管 | `timeline.py` / `actions.py` |
| 配置格式 | 卡片/控制键/预设/命名的 JSON schema | `persist.py`（schema 互读有回归） |
| UI 信息架构 | 五页签、卡片即按钮、双读、长按危险卡 | 三端各自实现，规范统一 |

**页面顺序、术语、危险操作规则**在三端一致——用户换设备不用重新学。

### 4.2 差异（为什么不能合并）

| 维度 | 方案 A | 方案 B |
|---|---|---|
| 传输 | UDP/OSC 直连台子 | HTTP 到电脑，电脑再发 OSC |
| 引擎位置 | 手机内 | 电脑内（浏览器发不了 UDP） |
| 状态来源 | 真台回读 | 电脑的虚拟台/真台镜像 |
| 更新 | 发版 + 重装（iOS 还要重签） | 刷新即最新 |
| 离线 | 无电脑也能用 | 必须有电脑 |
| 能力上限 | App 已实现范围 | 服务端全部 |
| 发现 | UDP 广播扫描 | 扫码 / 地址 |

### 4.3 一句话记住区别

> **方案 A 把"遥控器"放进手机；方案 B 把"调音台的大脑"留在电脑，手机只是屏幕和手指。**

## 5. 本轮实现：扫码进入（方案 B 的最后一公里）

### 5.1 为什么补这个

在此之前，进网页控制台只有一条路：**在手机上手工输入 `192.168.x.x:8080`**。
IP 记错、换网段、多人共用时极易出错。本轮把「输入 IP 或扫码」里的**扫码**补齐。

### 5.2 实现

| 组成 | 文件 | 说明 |
|---|---|---|
| 二维码编码器 | `x32sim/qr.py`（新增，纯标准库） | 字节模式、纠错 M、版本 1-10（≤213 字节）、8 掩码按 ISO 罚分择优 |
| HTTP 接口 | `x32sim/httpapi.py` `/qr.svg` | `?u=` 优先，其次 Host，最后局域网 IP；非 http(s) 或超长 → 400 |
| 终端二维码 | `x32sim/app.py` 启动横幅 | 半块字符（两行合一），深色终端反色映射；`--no-qr` 关闭；非 TTY 自动跳过 |
| 设置页卡片 | `web/index.html` / `app.js` / `app.css` | 白底二维码 + 地址 + 「复制地址」；`loadInfo()` 用 `/api/info` 的 `lanUrl` 生成 |

设计取舍：
- **不引第三方库**：服务端"仅标准库"是硬约束，二维码只有 ~230 行，自己写得起
- **二维码内容 = 页面上显示的那行地址**（不是另外算一份），避免"扫出来和看到的不一样"
- **终端二维码默认开、可在非交互环境自动关**：`sys.stdout.isatty()` + `--no-qr`
- **深色终端用反色映射**（浅块=浅色模块），出的是"浅底深块"的正确极性

### 5.3 验证（都是可复跑的）

| 验证 | 方法 | 结果 |
|---|---|---|
| 编码正确性 | `test_qr.py`：**解回原文** + 每块 RS 校验位全零 + 翻转 3 位后必失败 | 25/25（无第三方库环境） |
| 与独立实现一致 | 开发环境装 `python-qrcode`，**同版本同掩码逐位比对** | 5/5 样例一致，30/30 |
| 双形态一致 | `test_dual_form.py` 新增 `/qr.svg` 两形态逐字节比对 | 一致 |
| 接口边界 | `test_params.py`：200+SVG / 无参回落 / 非 http(s) 400 / 超长 400 | 5/5 |
| 真机尺寸 | 390×844 CDP 截图：二维码 222×222、白底、三定位角俱全 | 见 `outputs/shots/qr-settings-2026-10-23.png` |
| 端到端 | 抓取 `/qr.svg` 反解矩阵，与页面显示地址的矩阵逐位比对 | 一致（v3 / 29×29） |

### 5.4 踩到的三个坑（都已修）

1. **定时图形覆盖了定位图形**：先画定位图形再画定时线，会把定位图形竖边刷成浅色，
   整张码扫不出来。正确顺序是**先定时线、再由定位图形覆盖**两端。
2. **参考实现 segno 多写了一个 `0x00` 码字**：它在比特流已字节对齐时仍补 8 个 0
   （`8 - length % 8`），不符合 ISO 18004 §7.4.10。我按规范实现，改用
   `python-qrcode` 复核即完全一致。**别把"与某个库不同"直接当成自己错**。
3. **单文件形态 `NameError`**：`make_single` 会剥掉全部相对导入，`from .qr import svg as qr_svg`
   的别名随之丢失——包形态正常、单文件形态 500。已让合成工具**保留别名**（改写为赋值），
   并在双形态差分测试里加了 `/qr.svg` 守护。

## 6. 稳定性与安全性对照表

| 风险 | 方案 A | 方案 B | 状态 |
|---|---|---|---|
| 网络抖动 | 回读校验 + 自动重连 | 条件轮询 + 重试 + 红点提示 | ✅ |
| 弱网流量 | 只订阅需要的地址 | 11.7 MB/h（实测） | ✅ |
| 退后台 | iOS 会挂起（限制） | 浏览器后台降频 2 s | ✅ |
| 误触 | 长按 0.8 s + 键盘精调 | 同 | ✅ |
| XSS | 原生渲染无此面 | `esc()` + CSP | ✅ |
| 畸形输入 | 原生解析 | 入口校验 + 400 | ✅ |
| 未授权访问 | 局域网信任 | 局域网信任（**无鉴权**） | ⚠️ 见 §7 |
| 传输加密 | 无（OSC 明文 UDP） | HTTP 明文 | ⚠️ 局域网内可嗅探 |

结论：**在"家用/演出局域网"这个威胁模型下够用；一旦跨网段或公网暴露，必须先补 §7 的鉴权与 TLS。**

## 7. 遗留与后续（按价值排序）

1. **配对令牌（可选）**：QR 里带一次性 token（`/?t=...`），手输地址则要求 PIN。
   现在是"知道 IP 就能控"，加 token 不影响扫码体验，却能挡掉同网段误连。
2. **75 项参数面板进 App**：方案 A 目前只有演出操作，逐项调参仍要开网页。
3. **离线演示模式**：手机端本地虚拟台（现在只有 macOS 壳内置）。
4. **三端 dB 文案同步**：iOS/Android 仍用旧曲线（只影响显示）；规范 v1.7 已标注。
5. **真机核对 26 项出厂默认值**：`/api/info.calibration` + `tools/verify_defaults.py` 已就绪。

## 附：给使用者的最短路径

**方案 A（只看演出操作）**
1. 装 APK（Android）或 Sideloadly 签 IPA（iOS）
2. 手机与调音台接同一 WiFi
3. 打开 App → 自动发现或手输台子 IP:10023 → 开演

**方案 B（要卡片/桥接/全参数）**
1. 电脑装 Python 3，双击 `启动模拟器.bat`（首次放行防火墙）
2. 手机扫终端或设置页里的二维码 → 网页打开即是控制台
3. 安卓可「添加到主屏幕」，之后像 App 一样全屏用
