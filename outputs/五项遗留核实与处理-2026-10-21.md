## ① 压缩 / EQ / 发送 / Pre-Post：已补齐（并纠正了一处真错）

### 做了什么
参数登记表从 28 项扩到 **57 项**（16 既有 + 38 通道 + 3 发送），通道行从 14 字段到 **40 字段**：

| 类别 | 参数 | 地址 | 关键约束 |
|---|---|---|---|
| 动态 | on/thr/ratio/knee/mgain/attack/release/mix/pos | `/ch/NN/dyn/*` | thr 0.5 dB 档；ratio 线上是 **0..11 索引** |
| 均衡 | on + 4 段 ×(type/f/g/q) | `/ch/NN/eq/M/*` | 频率 201 对数档；Q 是**递减**对数表 |
| 发送 | level/on/tap | `/ch/NN/mix/MM/*` | 二维目标（通道 × Bus），512 个格子 |

为此给 ParamSpec 加了三种新能力：二维地址（`nidx=2`）、线上索引 ↔ 本地值换算
（`enum_wire="index"`）、反向对数（`logdesc`）。地址/量程/枚举全部对齐官方
**Behringer X32 Protocol Manual** 原文（`dyn/ratio enum {1.1…100}` 共 12 档、
`gate/thr linf[-80,0,0.5]`、`preamp/hpf logf[20,400,101]` 等）。

### 过程中抓到的两个真错
1. **`SEND_BY_FIELD` 用字段名建索引，而地址末段是 `type`**（字段叫 `tap`）。
   结果：OSC 读 `/ch/01/mix/03/type` **一条都匹配不上，且不报错**，只回空包。
   已改为按地址末段建表（`SEND_BY_SEG`），并留了守护用例。
2. **取点枚举写错了**：我原先按社区表写成 `{IN/LC, PreEQ, PostEQ, PreFader, PostFader, Sub}`（6 档）。
   官方原文是 `{<-EQ, EQ->, PRE, POST, GRP}`（**5 档**），且**只对奇数 Bus 定义**——
   真台按 1&2 / 3&4 成对共享取点。6 档表发过去会整体错位一档（"PRE" 被当成第 2 个值）。
   已按原文改，并让偶数 Bus 统一落到奇数搭档，本地只留一份真相。

### 前端
通道面板扩成四个分页（前置 / 动态 / 均衡 / 发送），共 42 行控件；发送走独立的
`/api/sends?ch=N`（512 项不进 `/api/state` 热路径）。频率类改用**对数滑块**
（1000 格映射）——线性 20..20000 在 390px 屏上一像素跳几十 Hz，根本落不到 100 Hz。

### 验证
- `test_params.py` **282 项**全过；全套 `run_all_tests.py` **8/8 组**通过
- 防漂移校验扩到 dec（显示精度）：`trim` 的 `dec=1` 配 0.25 dB 档会把 3.75 显示成 3.8，已改 2

## ③ trim ±18 vs 手册 ±12：在写入层收窄，不做发送时钳

**风险机理**：如果只在发送给真台时钳到 ±12，本地状态仍是 15 dB —— 界面显示 15、
台子实际 12，这种"差 3 dB"现场极难发现（推子推上去了，但没到他以为的位置）。

**处理**：量程覆盖走 `params.set_param_limits()`，在 `param_coerce` 里生效，
也就是**落库那一刻就收窄**。界面显示什么，台子上就是什么。

- 默认 **±18**（实测固件 1.15+ 是这个范围，手册的 ±12 是旧版）
- 老固件：`python x32_simulator.py --trim-range 12`，本地量程同步收到 ±12
- `/api/info` 回 `trimRange`，前端据此设滑块范围（不让用户拖到 18 再被弹回）
- 覆盖发生在 `load_user_config()` **之前**，避免"按宽量程读入、首次写入才收窄"的空窗

验证：`param_coerce('ch_trim',15)` 默认 15；收窄后 12；且只影响 trim，其它参数不变（6 项断言）。

## ④ 4G 流量账：22.5 → 11.7 MB/h（4 小时 90 → 47 MB）

新增 `tools/measure_traffic.py`，**按线上字节算（含请求/响应头，gzip 按压缩后计）**：

| 项 | 修复前 | 修复后 |
|---|---|---|
| 全量 `/api/state` | 44 065 B | **4 099 B** |
| 条件轮询（无变更） | 542 B | **322 B** |
| 电平 `/api/meters` | 1 070 B | **533 B** |
| **每轮（state+meters）** | 1 636 B | **853 B** |
| **折合** | **22.5 MB/h（4h 90 MB）** | **11.7 MB/h（4h 47 MB）** |

三刀，按收益排序：
1. **CSP 头只对 HTML 发**：每个 JSON 响应白背约 250 B，250ms 两轮 → 8 次/秒 ≈ **7 MB/h**，比响应体还贵
2. **协商 gzip**（>512B 才压）：全量包 43.5 KB → 4.1 KB
3. **电平数值收到 0.1 dB**：屏幕一像素约 0.5 dB，全精度是纯浪费；601 → 280 B

再加一刀**客户端**：页面不可见（锁屏 / 切 App）时轮询从 250ms 降到 2s。
按"屏幕亮 30% / 后台 70%"折算，4 小时演出约 **18 MB**。

⚠️ 测量方法上的坑：条件轮询必须带 `logseq`，否则服务端每次都把整段启动日志塞回来
（3 KB），量到的不是稳态。

**仍未结清**：本地 OSC 订阅推送（`_push_state_diffs`）只推变化值，但会**每 50ms 全表遍历**
一次（CPU，不是流量）；且 `PUSH_CACHE` 是全局的，**新订阅者收不到初始全量**——
这是功能缺口，不是流量问题，留待下一轮。

## ⑤ WriteSink 与键盘精调：前者早已落地，后者本轮补上

**WriteSink 不是未完成项**。查代码确认它已在模块化（B4）时落地：

```python
# state.py
class WriteSink:  def on_write(self, kind, idx, value, source): ...
SINKS = []        # 由 app.py 注册

# app.py
def _register_sinks():  SINKS.append(BRIDGE_SINK)
```

`state` 不再 import `bridge`，转发只拿**落库后**的值（B0-2 的根因由此封死）。
之前记忆里写"未落地"是旧信息，已更正。回归里 bridge 组 18/18 覆盖了这条链路。

**键盘精调**本轮补上：面板里数值标签可点，点开变 `number` 输入框
（`inputmode=decimal`，手机上直接弹数字键盘），Enter 提交 / Esc 取消 / 失焦提交。
实测：输入 3.75 → 台面 `trim=3.75`（0.25 档量化保留）。
