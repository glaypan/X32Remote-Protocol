# 自动增益 / 自动推子（Vocal Rider 式）设计与实现

> 日期：2026-10-23 · 服务端规范 v1.7+ · 新增模块 `x32sim/rider.py`
> 一句话：给每路一个"目标电平"，按电平自动走**推子**或**数字增益**，
> 三档速度、平均与死区保证**不会一格一格地抽**，并且真的在动台子。

---

## 1. 需求 → 实现映射

| 需求 | 落点 |
|---|---|
| 控制端设目标电平（如 -18 dBFS） | 每通道 `target`，默认 -18，可 -60..0 实时改 |
| 用调音台返回的电平数据 | 服务端 `compute_levels()`（与网页电平表同源），50 ms 一拍 |
| 自动增益 **或** 自动推子 | `mode = gain` → `ch_trim`；`mode = fader` → `ch_fader` |
| 实时修改 | 配置无重启生效，下一拍（≤50 ms）按新参数跑 |
| 体现真实台面操作 | 写入走 `set_value(..., source="auto")` 同一条管道，桥接时真实下发 OSC |
| 三档修改速度 | `slow / medium / fast` = 平均窗口 / 死区 / 每秒最大修正 |
| 电平要平均，不能突然改 | 线性功率指数平均 + 死区 + 速率限制（三条缺一不可） |
| 参考 Waves Vocal Rider | 同样"骑"在目标上；差异见 §7 |

## 2. 先解决一个会自激的坑：电平从哪来

原来的电平表是**用推子位置算出来的**：

```
电平 = fader_to_db(推子) + 抖动
```

自动推子一接上就会出事：目标比当前低 → 拉低推子 → 表跟着变低 → 控制器以为"还不够" → 再拉低……
最后推子到底、声音没了。这不是控制器调参能救的，是**被控对象建模错了**。

现在拆成两个量（`state.source_level_db`）：

```
信号源 (话筒实际在唱多大) + 数字增益 + 推子 = 电平表
```

- 信号源是独立的"音乐化"波形（0.7 Hz + 3.1 Hz + 0.15 Hz 三个正弦叠加，约 ±8 dB，每路相位错开）
- 数字增益（trim）与推子都作用在信号源之上 —— 与真台的信号流一致
- 表格里看到的、控制器读到的，都是这个叠加结果

这样"拉低推子 → 电平下降"仍然成立（闭环），但控制器是在**控制一个真正的被控对象**，
而不是控制自己造成的回声。

---

## 3. 控制律：三条平滑，缺一不可

```
误差 = 目标 - 平均电平
① 平均：线性功率的指数滑动平均（窗口随速度 0.9 / 0.35 / 0.12 s）
② 死区：|误差| < 0.6 / 0.4 / 0.3 dB → 不动
③ 速率：每拍最多走 1.5 / 5 / 15 dB 每秒（50 ms 一拍 → 0.075 / 0.25 / 0.75 dB）
```

为什么三个都要：

- **只用瞬时值**：每个字都改一次推子，听起来是颤音（这是很多"自动增益"插件最难听的地方）
- **只平均不死区**：平均值在目标附近微抖，推子会持续"呼吸"，演出时听得出机械感
- **只有前两个不限速**：安静段突然出声，一帧把推子从 -40 拉到 0，就是明显的音量台阶

三档速度的实际差别（同一段素材，达到目标所需时间）：

| 速度 | 平均窗口 | 死区 | 速率上限 | 体感 |
|---|---|---|---|---|
| 慢 | 0.90 s | 0.6 dB | 1.5 dB/s | 几乎听不出在动，适合稳态演唱 |
| 中（默认） | 0.35 s | 0.4 dB | 5 dB/s | 跟得上句子，不抢 |
| 快 | 0.12 s | 0.3 dB | 15 dB/s | 贴得紧，适合说话/脱口秀 |

## 4. 两种执行器

| 模式 | 写什么 | 表现 | 适用 |
|---|---|---|---|
| `fader` | `ch_fader`（推子 0..1） | 接真台时电动推子会自己走，**看得见** | 演出中需要"看得见的自动" |
| `gain` | `ch_trim`（数字增益 ±18 dB） | 推子不动，电平在输入侧被拉齐 | 推子要留给手动、或想保持推子位置语义 |

两者都通过 `set_value(..., source="auto")`：

- 走与卡片/手动同一个写出口 → 桥接模式下真实下发 `/ch/NN/mix/fader`、`/ch/NN/preamp/trim`
- 桥接限速表新增 `auto: 0.1 s`，不会把真台刷爆
- `source` 不是 `manual`，因此不会触发"手动接管"冲突逻辑

---

## 5. 安全边界（都会实际发生）

| 情况 | 行为 | 为什么 |
|---|---|---|
| 静音 / 无信号（≤ -80 dB） | 冻结，并清空平均值 | 否则会把静音一路推到 +12 dB，一开麦就是爆音 |
| 卡片正在渐变这一路 | 让位（不写） | 时间轴与控制器抢同一个推子，两边都会抖 |
| 有人手动拖了推子/拧了增益 | 暂停 2 秒，并把量程基准挪到新位置 | 人的操作优先；2 秒后从新位置继续 |
| 目标超出量程 | 停在 ±range（默认 12 dB） | 量程是**累计**限制，不是单拍限制（早期实现只限单拍，推子会一路爬到顶） |
| 推子到 0 / 1 两端 | 停手 | 不硬顶，避免"看似在调其实没变化" |

> "检测人工干预"没有去改 `set_value` 的每条路径，而是**记住自己上次写的值**：
> 当前值与它差超过 0.25 dB，就认定是别人动的。这样对外部 OSC、网页推子、控制键一视同仁。

## 6. 接口与界面

**HTTP**

```
GET  /api/rider                    → {enabled, speeds, modes, channels:{...实时值}}
POST /api/rider  {"channel":3,"on":true,"target":-18,"mode":"fader","speed":"fast"}
POST /api/rider  {"channel":"all","on":false}
POST /api/rider  {"channel":3,"remove":true}
POST /api/rider  {"action":"reset"}      # 清平滑状态（从当前电平重新起算）
POST /api/rider  {"enabled":false}       # 总开关
POST /api/rider  {"channel":3,"tap":"pre"}                    # 表源：pre / post
POST /api/rider  {"channel":3,"sidechain":5}                  # 侧链：用第 5 路电平判断
POST /api/rider  {"channel":3,"curve":{"loop":30,
                  "points":[[0,-24],[15,-16],[30,-24]]}}     # 目标曲线（null 清除）
```

`/api/state` 里带一份紧凑快照 `rider.on[]`（只含启用通道）：
`{ch,target,mode,speed,level,applied,paused}` —— 界面用它画实时条，不额外轮询。

**界面**：新增页签「自动」（第 5 个页签，在"控制键"之后）

- 顶部总开关 / 通道号添加 / 清空修正
- 每通道一张卡：启用、推子|增益、慢|中|快、目标 dBFS、删除
- 实时：彩条（电平）+ 一行文字 `电平 -20.5 dBFS · 修正 2.8 dB · 目标 -18.0`，
  人工接管时显示「人工接管中」，无信号显示「冻结中 · 不会往上推」
- 配置落 `user_config.json` 的 `rider` 键，逐条消毒（非法通道/速度/量程丢弃或钳制）

## 7. 与 Waves Vocal Rider 的对照

| 维度 | Vocal Rider | 本实现 |
|---|---|---|
| 检测 | 输入电平（可侧链） | 通道电平（推子后，与界面同源） |
| 目标 | 可写目标曲线（riding target） | 固定目标值（后续可加曲线） |
| 平滑 | 内置 attack/release + 灵敏度 | 功率平均窗口 + 死区 + 速率限制 |
| 速度 | 连续可调 | 三档（按需求） |
| 执行 | 推子（自动化写入 DAW） | 推子 **或** 数字增益（直接发 OSC 到台子） |
| 静音处理 | 有 gate/hold | ≤ -80 dB 冻结 + 清平均 |
| 人工干预 | 手动时让位 | 自动检测并暂停 2 s |

差异主要在"目标曲线"和"侧链"：这两项没做，属于后续增强（见 §9）。

| 项 | 断言 |

## 9. 已知限制与后续（v1.4.0 已补齐前四项，见 §12-§15）

1. **真台的电平取点**：本实现用"通道表"（推子后）。接真台时若表是推子后的闭环也没问题，
   但如果台子有延迟/平滑，建议用 pre-fader 表；目前没有做"表源可切换"的开关。
2. **目标曲线**（Vocal Rider 的 riding target）没做：现在是固定值。
3. **侧链触发**（按另一路电平骑这一路）没做。
4. **iOS / Android 未接入**：只有网页/macOS 壳有界面；协议是 `POST /api/rider`，两端接起来不难。
5. **数字增益的固件量程**：写死 ±18 dB，旧固件 ±12 时会被服务端钳制（`/api/info.trimRange` 已提供）。

## 12. 目标曲线（Vocal Rider 的 riding target）

固定目标解决不了"主歌要小、副歌要大"：主歌 -24 dB、副歌 -16 dB，中间还得平滑过渡。
所以加了**时间-电平**的点列曲线：

```
curve = {"loop": 30, "points": [[0,-24], [15,-16], [30,-24]]}
```

- **0 时刻 = 本次启用（或点「清空修正」）的时刻**，不是开机时间 —— 否则每次打开页面
  都从曲子中间开始，行为不可预测
- 线性插值，两端钳住；`loop > 0` 时按周期折返（`t mod loop`）
- 曲线生效时**固定目标自动置灰**：两个目标同时存在一定会有人搞混
- 消毒：点按时间排序、同一时刻后写覆盖、时间 0-3600s、电平 -60..0 dB、最多 32 点、单点视为非法

**界面**：每通道一条 84px 高的曲线图。

| 操作 | 行为 |
|---|---|
| 空白处点一下 | 在落点加一个点（自动按时间排序） |
| 按住点拖动 | 改这个点的时间/电平（实时重绘，松手才落库） |
| 双击点 | 删除（少于 2 点时整条曲线清除） |
| 「循环」输入 | 0 = 不循环；小于最后一点时自动抬到最后一点 |

为什么不做"画自由曲线"：拖一个点就知道结果，比画笔可控；而且点列能直接存 JSON、
两端（网页 / App）读同一份数据。

## 13. 侧链触发

`sidechain = 0` 用本通道电平（默认）；`1-32` 用**另一路**的电平来判断，但仍然修正本通道。

典型用法：主持人话筒压着背景音乐——音乐那一路开自动推子，侧链选主持人通道；
主持人一说话，音乐自动让开，说完自己回来。

实现只改了取电平那一行（`measure()`），控制律完全复用 —— 侧链不是特殊模式，
只是"看哪一路"的参数。侧链通道越界会回落到本通道（不能因为一个脏参数把某路推飞）。

## 14. 表源：推子前 / 推子后

| `tap` | 测量什么 | 特性 |
|---|---|---|
| `post`（默认） | 电平表（推子后） | 闭环：控制器能看到自己的动作，稳态精确；但推子与测量互相影响，必须靠速率/死区约束 |
| `pre` | 信号 + 数字增益（推子前） | 开环：**推子怎么动都不影响测量**，最稳，适合"推子还要手动用"的场合 |

两条路的差别在测试里是硬断言：推子从 0.5 拉到 0.9，`pre` 的测量值必须**一模一样**，
`post` 必须跟着变。

> 接真台时：X32 的通道表默认是推子后；要用 `pre` 得把 meter tap 改成推子前。
> 这也是为什么默认给 `post` —— 不依赖台子的表配置也能工作。

## 15. iOS / Android 接入

两端都不重写控制律 —— **控制律在电脑端服务里跑**（它要读电平表、50ms 一拍），
手机只做配置与显示。协议就是 `GET/POST /api/rider`，与网页端完全同一份。

| | 入口 | 实现 |
|---|---|---|
| Android | 顶栏「菜单」→「自动增益 / 自动推子」 | `core/RiderApi.kt`（HttpURLConnection）+ `ui/RiderDialog.kt` |
| iOS | 新增「自动」页签 | `X32RemoteCore/Rider/RiderClient.swift`（URLSession + Codable）+ `App/Views/RiderView.swift` |

两端一致的能力：总开关、添加/删除通道、启用、推子/增益、慢中快、目标 ±0.5、
每 0.8s 刷新电平与修正值、显示"曲线""侧链""推子前""人工接管中"状态。

前提写在使用处：**需要电脑端服务在跑，手机与电脑同一网段**。手机上单独一个 App
是算不出这个功能的（它没有电平历史，也不该每 50ms 往台子写一次）。
