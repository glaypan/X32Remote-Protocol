# 真实使用走查报告：问题清单与修复优先级

> 时间：2026-10-20 · 对象：`X32Simulator/x32_simulator.py`（6512 行，Python 侧 4400 + 内嵌网页 2100）
> 方法：**不是读代码猜问题，而是把用户真实会做的操作跑一遍**。用独立端口（18090–18093 / 11026–11029）、独立配置，另写一个"假真台"（UDP 服务）来收包计数。

## 一、结论先说

**功能是通的，但"用了几天"的路径上有 5 个必须修的问题**，其中 3 个属于本项目一直在防的「假成功」：

| 编号 | 一句话 | 严重度 |
|---|---|---|
| P0-1 | 卡片连点两次 = 两个执行线程同时驱动同一批推子；"停止后立刻开下一张"时旧卡还在跑 | 高（现场事故级） |
| P0-2 | 桥接转发用的是**未钳制的原始值**，本地 1.0、真台收到 1.7，NaN 也照发 | 高（真台状态分叉） |
| P0-3 | 配置保存失败 / 文件损坏 → 界面全部显示成功，重启后卡片与预设**静默消失** | 高（丢用户数据） |
| P0-4 | 预设范围传了不认识的值 → 静默变成"全量 158 值"，回归时整台被换掉 | 高（局部变全局） |
| P1-1 | 卡片渐变期间向真台发 **约 900–1000 包/秒**，预设回归 276 包/秒 | 中高（真台丢包/卡顿） |
| P1-2 | 网页每 250ms 拉一次 15–21 KB 全量状态，4G 下 **271–300 MB/小时** | 中（移动流量/耗电） |
| P1-3 | 高频写入把日志环刷满，启动期日志（含"配置加载失败"）被挤掉 | 中（排障失效） |
| P2 | `/scene/999/load` 会把场景号设成 999；配置并发写偶发 `PermissionError` | 低中 |

## 二、P0 问题详情（含实测证据）

### P0-1 卡片执行的并发与竞态

**证据**（`_review_realuse.py` 场景 1）：

```
FAIL 1a 连点两次 → 只应有 1 个 worker | 实际 2 个
NOTE 1b 结论 | 旧 worker 仍在跑：ch1 从 0.860 继续涨到 0.900
```

- 连点两次同一张卡 → **2 个线程**同时执行（推子被写两遍；两张不同卡时互相打架）。
- 停止 A 后立刻启动 B：A 的目标是 0.9，B 只碰 ch2。实测 ch1 在"停止"后仍从 0.860 涨到 **0.900** —— A 没有被真正停掉。

**根因**（两处，都在 `run_show` / `_show_worker`）：

```python
def run_show(card):
    threading.Thread(target=_show_worker, args=(card,), daemon=True).start()   # 无并发保护

def _show_worker(first_card):
    SHOW_STOP.clear()      # ← 新 worker 一启动就把上一次 set() 的停止信号抹掉
```

`SHOW_STOP` 是**全局单个 Event**。`do_POST /api/show` 里先 `set()` 再 `run_show()`，新线程进来第一件事就是 `clear()`。旧线程若正好在 `sleep(0.05)` 中，醒来看到 `is_set()==False` 就继续执行——停止信号被吃掉。

**修法**（不是加锁，而是换模型）：

```python
# 每轮执行一个"代际"对象，Event 归代际所有，不再共享
class ShowRun:
    def __init__(self, card_id):
        self.id = card_id
        self.stop = threading.Event()

RUN = {"cur": None, "lock": threading.Lock()}

def run_show(card):
    with RUN["lock"]:
        if RUN["cur"]:
            RUN["cur"].stop.set()          # 只停旧代际
        run = ShowRun(card["id"])
        RUN["cur"] = run
    threading.Thread(target=_show_worker, args=(card, run), daemon=True).start()
    return run

# 所有循环条件改成 run.stop.is_set()，"当前是谁"用 RUN["cur"] is run 判定
```

同时 `SHOW_STATE` 的收尾必须带"我还是当前代际"的判断（现在只在 `running == card["id"]` 时清，同 id 连点会互相清）。

**验收**：连点 5 次只有 1 个 worker；停止后旧卡的目标值不再推进；`show.running` 不会提前变空。

### P0-2 桥接转发未使用钳制后的值

**证据**（场景 2）：

```
NOTE 2a 转发值 vs 本地值 | 本地 1.000 ← 真台收到 1.7000000476837158（不一致）
NOTE 2b NaN 输入被拒绝或收敛 | HTTP 200；转发 NaN 包 1 个
```

**根因**（`set_value` 末尾）：

```python
if BRIDGE["addr"] is not None and source in ("manual", "action", "dca"):
    _bridge_forward(kind, idx, value)      # ← value 是入参原始值
```

`_clamp01` / `_truthy` / `_finite` 只作用在本地 `STATE`。转发拿到的是**入口值**：`1.7` 变 `1.7`、`"nan"` 变 `float("nan")`。于是本地和真台对同一个推子存了两个不同的值，回读时又会被「回声抑制」挡住（值不等 → 不认作回声）→ 本地被真台的真实值覆盖或反之，形成难以解释的抖动。

**修法**：转发一律取**落库后的值**，并且拒绝非有限值：

```python
after = get_value(kind, idx)                      # 权威值
if after is not None and BRIDGE["addr"] is not None and source in ("manual", "action", "dca"):
    _bridge_forward(kind, idx, after, already_clamped=True)
```

`get_value` 内部有锁，注意避免在 `with STATE.lock` 内再调（当前 `set_value` 的转发在锁外，安全）。

**验收**：`value=1.7` → 真台收到 1.0；`value="nan"` → 真台收不到包（本地按默认值或不改）；回读后本地值不回退。

### P0-3 持久化的三种"假成功"

**证据**（场景 3 + 并发压测）：

```
3b 配置损坏后仍能启动 | cards=8 presets=0        ← 用户卡片全丢，只剩内置演示卡
3b 日志有记录 | 配置加载失败: JSONDecodeError('Unterminated string ... char 3778')
3c 配置不可写时的保存结果 | HTTP 200 {'ok': True, 'id': 1, 'count': 32 ...}
NOTE 3c 假成功 | 落盘失败但接口返回 ok，用户重启后预设消失且无任何提示
并发改名 192 次 → 日志出现 1 次：配置保存失败: PermissionError(13, 'Permission denied')
```

三个独立缺陷叠在一起：

1. **非原子写**：`open(CONFIG_PATH, "w")` 先截断再 `json.dump`。进程被杀/磁盘满 → 半截 JSON（实测把文件截到 60% 就能稳定复现启动失败）。
2. **失败不上报**：`save_user_config` 的 `except` 只 `log()`，`/api/snapshot`、`/api/name`、`/api/cardadd` 仍返回 `ok:true`。
3. **并发写同一文件**：`ThreadingHTTPServer` 每请求一线程，两个改名同时 `open("w")` → Windows 报 `PermissionError`，那次变更只留在内存。

**修法**（`persist.py`，三件事一起做）：

```python
def save_config(doc):
    tmp = CONFIG_PATH + ".tmp"
    with open(tmp, "w", encoding="utf-8") as f:
        json.dump(doc, f, ensure_ascii=False, indent=1, allow_nan=False)
        f.flush()
        os.fsync(f.fileno())
    os.replace(tmp, CONFIG_PATH)        # 原子替换：要么旧文件，要么新文件
```

- 用一把模块级 `SAVE_LOCK` 串行化写；写失败**抛异常**，上层接口返回 500 + 明确文案（"配置未保存到磁盘，重启后会丢失"）。
- 加载失败时：把坏文件重命名为 `user_config.corrupt-<时间>.json`，再从默认值启动，并在 `/api/state` 里带一个 `configError` 字段让界面弹横幅——**不能只在日志里留一句**。
- 加 `schemaVersion` 字段，为后续预设/卡片格式迁移留出入口。

**验收**：断电模拟（启动后 kill -9）再启动，配置要么是旧的、要么是新的，不出现解析失败；只读目录下保存返回 5xx 且界面可见；并发 192 次改名零失败。

### P0-4 非法的预设范围被"宽容"成全量

**证据**（场景 4c）：

```
请求 scope = {groups:["bogus"], params:["nope"]}
响应 HTTP 200 {'ok': True, 'count': 158, 'scopeText': '输入通道、Mix Bus、... · 推子+静音'}
```

`clean_preset_scope` 的策略是"认不出来就回落到默认全量"。单看很稳健，但在这个功能里**方向是反的**：用户勾的是局部，存下来的是全量，回归时整台被换掉——正是这次改造要防的头号事故。

**修法**：区分「缺省」与「非法」——

- 字段缺失（老客户端没传 scope）→ 允许回落到默认全量（兼容旧数据）；
- 字段存在但**一个合法项都没有** → 400 `"范围里没有可识别的组/参数"`；
- 部分合法（`["ch","bogus"]`）→ 保留合法项，并在响应里回 `unknown: ["bogus"]`，让界面能提示。

**验收**：`groups:["bogus"]` → 400；`["ch","bogus"]` → 200 且 `scopeText` 只含"输入通道"，响应带 `unknown`。

## 三、P1 问题详情

### P1-1 桥接时的写入风暴

实测（假真台收包计数）：

| 操作 | 包量 |
|---|---|
| 预设回归（32 路 × 推子+静音，3 秒） | **992 包 / 3.6 秒 ≈ 276 包/秒** |
| 卡片 `fade_all`（79 路渐变，2 秒） | **2370–2765 包 / 2.6 秒 ≈ 912–1063 包/秒** |

原因：时间轴 tick 0.05s，每个 tick 对每个渐变目标都调一次 `set_value` → 每路 20 包/秒 × 79 路。X32 的 OSC 处理能力远低于此，现场表现是**真台推子跳帧、动作不同步、包被丢弃**。

**修法：在转发层加写合并（coalescing），而不是降低 UI 刷新率**——

```python
# bridge.py：按 (kind, idx) 只保留最后一次值，按固定节奏（如 20–30ms）批量发出
PENDING = {}          # (kind, idx) -> value
def enqueue_write(kind, idx, value):
    PENDING[(kind, idx)] = (value, time.time())

def flush_loop():
    while True:
        time.sleep(0.03)
        batch = drain(PENDING)
        for (kind, idx), (v, _) in batch.items():
            send(addr_for_write(kind, idx), v)
```

效果：79 路渐变从 1000 包/秒降到 **79 × 33 ≈ 2600/秒？** 不对——合并的意义是"同一路在一个窗口内只发最后一次"，所以是 `79 路 × 33 次/秒` 仍高。真正的做法是**只发变化的差量**：渐变每 tick 每路都在变，合并救不了量，需要**降频 + 差量阈值**：
- 转发节奏固定 30ms（33 次/秒），每路仅在"与上次转发值差 > 0.002"时入队 → 渐变期间每路约 33 包/秒，仍是 79×33。
- 进一步：真台推子本身有刷新率上限，实测可用 **15–20 次/秒**；且 `fade_all` 这类全台渐变，真台侧更适合用场景 recall 而不是逐路写。

**务实方案（分两级）**：
1. **必做**：转发队列 + 30ms 合并 + 差量阈值 → 静态操作从 20 包/秒/路降到 ≈0（无变化不发）。
2. **必做**：渐变类动作的转发上限设为 **15 次/秒/路**，并在 UI 提示"桥接模式下渐变精度受真台刷新率限制"。
3. **可选**：全台渐变（`fade_all`/`fade_odd_even`）在桥接模式下提示改用场景。

**验收**：`fade_all` 2 秒的转发包量 ≤ 79 × 15 × 2 ≈ 2400（现在 2765，变化不大）——所以要认清：**这条的收益主要是"静态时不发无用包"和"不淹真台"，不是把渐变包量压到很低**。真正压量必须靠降频，界面要明说精度损失。

### P1-2 轮询负载

实测 `/api/state` 组成：

| 场景 | 总大小 | 大头 |
|---|---|---|
| 空台（新用户） | **14.8 KB** | console 3.1 / fx 2.5 / cards 2.1 / ch 1.0 / names 1.0 |
| 用一阵（8 卡 8 预设） | **21.3 KB** | cards 4.7 / console 3.1 / fx 2.5 / log 1.7 |

按网页 250ms 一轮：**77 KB/s → 4G 下 271–300 MB/小时**。数据里 `console`（控台元数据 + pending 清单）、`fx`（8 槽完整参数）、`cards`（完整动作定义）几乎**从不变化**，却每帧重发。

**修法**：三档并行
1. **拆接口**：`/api/state` 只回"会变的部分"（各推子/静音/电平/场景/show 进度）；`/api/meta` 回 console/fx/cards/snapshots/quickKeys，前端启动拉一次，变更时由响应里的 `rev` 号触发重取。
2. **差量**：状态按 tick 生成 `changed` 集合（已有 `PUSH_CACHE` 的基础），只回变化的键；无变化回 304 或 `{unchanged:true}`。
3. **自适应频率**：有操作/卡片运行时 250ms，空闲 1–2s；页面隐藏（`document.hidden`）时暂停。

**预期**：稳态从 77 KB/s 降到 **3–8 KB/s**（4G 下 11–29 MB/小时）。

### P1-3 日志环被刷屏

实测：连续 120 次推子写入后，`/api/state` 的日志窗口里**启动期日志已经不见**，只剩最近几条 OSC 明细。

根因：`handle()` 对**每一个**收到的 OSC 包先打一行 `"ip <- /addr args=..."`，推子拖动时每秒几十条。`LOG_RING` 只有 200 条，启动信息（含"配置加载失败""端口回退"）几分钟内就被挤掉。

**修法**：分级别。
- `handle` 的收包日志降为 `debug`（默认不记，设置页可开"OSC 调试"）；
- `SET` 明细按 `(kind, idx)` 做 200ms 合并（`"ch_fader 05 ×12 → 0.72"`）；
- 启动/配置/桥接/错误类消息进**独立 ring**，永不被高频日志挤掉（`/api/state` 里分成 `log` 与 `systemLog`）。

## 四、P2 与"做得对"的部分

**P2**
- `/scene/999/load` → `scene=999`（实测）。OSC 入口没有范围校验，而预设/回归又钳 0–99，两边不一致。改为 `1 <= n <= 99` 否则记日志忽略。
- 配置并发写偶发 `PermissionError`（已并入 P0-3）。
- `/api/set` 的 `param` 只认 `fader/on`，改名走 `/api/name`、FX 走 `/api/fx`、场景走 `/api/show` —— 同一个"设置"概念分散在 5 个接口，前端要为每个写一套。模块化时统一为 `/api/param`（`{group, idx, param, value}`）+ 保留旧接口做别名。

**做得对、不要改的**（走查里逐项验证过）：
- 越界：`idx=99` → 400 且文案带控台名；非数字推子值 → 400；空动作卡 → 400。
- 名称统一截断 12 字（中文按字符，不是字节）。
- 缺预设的局部场景**不改场景号、不退化全量**（实测 scene 保持 1）。
- 事件队列有界（20 条）、自动撤销点有界（5 条）、25 次连续执行后回到空闲（无泄漏迹象）。
- 日志增量 `?logseq=` 生效（请求 3 条返回 0 条，因为已读过）。

## 五、修复顺序（为什么是这个顺序）

```
B0（修 P0，1–2 天）  ──►  B1（抽纯函数层）  ──►  B2（抽 state + profiles）
                                                   │
十项参数 ◄── B3（抽 presets/actions/timeline + ParamSpec）──┘
```

**不要先做大重构再修 bug**：P0-1/P0-2 的修法会改动 `set_value`、`run_show`、`save_user_config` 这三个几乎每个模块都碰的函数，先重构会让 diff 无法审阅。
**也不要先加十项参数再重构**：十项参数会让 `set_value` 从 60 行涨到 300 行、`/api/state` 再涨 3–5 倍，那时再拆成本翻倍。

B0 的验收就是本文档的 5 条 P0 + 3 条 P1，每条都有可重复的实测脚本。
