# 模块化搭建方案（v1 草案）

> 目标：在**不破坏现有分发链路**（macOS App 内嵌、在线版 `python3 x32_simulator.py`、协议仓按 tag 拉单文件）的前提下，把 6512 行单文件拆成可长期维护的模块，并为「十项通道参数」这类扩展留出"填表即接入"的位置。

---

## 一、为什么现在必须拆（不是审美问题）

当前 `x32_simulator.py` 的实际结构：

| 区段 | 行数范围 | 内容 | 变更频率 |
|---|---|---|---|
| OSC 编解码 | 46–141 | 编解码 + 地址匹配 | 极低 |
| 常量 / FX 元数据 | 142–288 | 容量、默认名、FX 库 | 低 |
| 控台驱动 | 289–513 | X32/M32/Wing/Yamaha/A&H + 地址映射 | 中（加控台时集中改） |
| 状态与数据面 | 514–1514 | `MixerState`、`get/set_value`、DCA 级联、桥接、推送、电平 | **极高** |
| 端口/启动 | 1515–1673 | 解析、端口优先级、`main()` | 低 |
| 卡片/定时/冲突 | 1674–2028 | `SHOW_STATE`、调度、冲突检测 | 高 |
| 预设 | 2029–2408 | scope、抓取、回归 | 高 |
| 控制键/持久化 | 2409–2706 | 快捷方式、`save_user_config` | 中 |
| 动作内核 | 2707–3519 | set/osc/label/fade/timeline/清洗（813 行） | **极高** |
| 状态聚合 | 3520–3651 | `snapshot_state`、消毒 | 高（每次加参数都要改） |
| HTTP API | 3652–4408 | 29 个路由挤在一个 `do_POST` 里（757 行） | **极高** |
| 内嵌网页 | 4409–6507 | 2098 行：CSS 209 + JS 1565 + 116 个函数 | **极高** |

三个具体痛点，都是加参数时会立即放大的：

1. **加一个参数要改 8 处**：`MixerState` 字段 → `get_value` 分支 → `set_value` 分支 → `SET_KINDMAP` → 驱动 `addr` → `snapshot_state` → `/api/state` → 前端控件。任一处漏了就是「接口 ok 但界面不动」。
2. **29 个路由一个函数**：`do_POST` 757 行，加接口时 diff 必然和别人的改动撞。
3. **前端 1565 行 JS 在一个 Python 字符串里**：没有语法检查、没有模块、改一行要跑整个页面；编辑器的补全/跳转全部失效。

**结论**：先拆，再扩。否则十项参数会让"状态与数据面"和"动作内核"两个区段各涨 300+ 行。

## 二、硬约束：必须保留"单文件可分发"

这是本项目最容易做错的地方。当前有三条链路依赖"一个 `.py` 文件"：

```
① 在线版     workbuddy sites: language=python, startCmd=python3 x32_simulator.py
② macOS App  CI 从协议仓按 tag 拉 x32_simulator.py → 塞进 Contents/Resources
③ iOS/Android 不直接跑，但协议仓里的这份单文件是"权威实现"的对照物
```

所以方案不采用"拆完就变成包"，而是**双形态**：

```
开发形态（仓库）          x32sim/ 包 + 若干模块 + tools/make_single.py
        │
        └─ 构建 ─────────► 分发形态（产物）dist/x32_simulator.py（单文件，自动生成，禁止手改）
                                    │
                                    ├─► 在线版部署目录
                                    ├─► macOS CI 拉取对象（协议仓 release 附件）
                                    └─► 协议仓根目录（只放产物）
```

`tools/make_single.py` 的规则（简单、可审计）：

- 按**拓扑序**拼接模块（依赖在前），每段前面加 `# ==== x32sim/xxx.py ====` 标记；
- 把 `from .foo import bar` / `from x32sim.foo import bar` 改写成无操作或直接删掉（拼接后都在同一命名空间）；
- 只允许**绝对导入**，禁止在模块顶层做有副作用的初始化（否则拼接到单文件后执行顺序会变）；
- 产物开头写 `# AUTO-GENERATED by tools/make_single.py — DO NOT EDIT`；
- 生成后跑一次 `python dist/x32_simulator.py --selftest` + 全量回归，绿了才算发布。

**验收**：`dist/x32_simulator.py` 与拆包前的 `wc -l` 差异 < 5%，行为完全一致（回归 + CDP 截图比对）。

## 四、模块边界与依赖方向

### 4.1 依赖规则（用 `check_layers.py` 强制）

```
        app
         │  装配一切，唯一允许知道全部模块的地方
         ▼
      httpapi ──────────────► cards / presets / actions / state / persist / scan
         │                        │
         │                        ├── actions ──► state
         │                        ├── presets ──► state
         │                        └── cards   ──► actions.timeline
         ▼
       state ──► params / profiles / osc
         │
         └── sinks（注册制）：bridge / push / conflict，由 app 注册
```

三条禁令：
1. **`state` 不许 import `bridge`**（现在 `set_value` 里直接调 `_bridge_forward`，是耦合的根源）；
2. **`actions` 不许 import `httpapi`**（动作执行不知道 HTTP 存在）；
3. **`osc` / `params` / `consts` 不许 import 任何其它业务模块**（纯函数层，可被单测直接覆盖）。

### 4.2 关键抽象：写出口（Write Sink）

这是整个重构里唯一需要设计的接口，其余都是搬运：

```python
# state.py
class WriteSink:
    def on_write(self, kind, idx, value, source): ...

SINKS = []                       # 由 app.py 注册，state 不知道具体是谁

def set_value(kind, idx, value, source="manual"):
    ...                          # 校验 + 落库 + 取落库后的值
    after = _read_locked(kind, idx)
    for s in SINKS:
        s.on_write(kind, idx, after, source)      # 一律传"落库后的值"
```

收益（一次性解决三个 P0/P1）：
- P0-2 转发未钳制值 → sink 只能拿到 `after`，物理上不可能再发原始值；
- P1-1 写风暴 → `bridge` 作为 sink 内部做合并/降频，`state` 不用改；
- 冲突检测 / 推送 / 日志合并 都是 sink，互不干扰。

### 4.3 ★ ParamSpec：让"加参数"变成填表

`params.py` 是这次重构最重要的产出。每个可读写参数一条描述：

```python
ParamSpec = {
    "ch.gain": dict(
        group="ch", key="gain", label="增益", unit="dB",
        kind="float", range=(-18, 48), default=0, step=0.5,
        osc="/ch/{idx:02d}/preamp/trim",               # 写地址
        read="/ch/{idx:02d}/preamp/trim",              # 读地址（通常同写）
        preset=True, card=True, quick=False,
        fmt="{:.1f} dB", verify="真机标定",
    ),
    "ch.fader": dict(group="ch", key="fader", label="推子", unit="dB",
                     kind="float", range=(0.0, 1.0), default=0.75, step=0.01,
                     osc="/ch/{idx:02d}/mix/fader", preset=True, card=True, quick=True),
    ...
}
```

然后：
- `state.get_value/set_value` 由表驱动，不再写 8 个 `if`；
- `snapshot_state` 由表生成（前端拿到的字段自动同步）；
- 预设的 `PRESET_GROUP_PARAMS` 由 `preset=True` 推导；
- 动作白名单的 `set` 目标由 `card=True` 推导；
- 前端参数面板由 `/api/meta.params` 生成（**一次改表，三端同时生效**）；
- 未标定的参数（`verify` 未通过）自动 `ready=False`，写入被拒并提示"需真机标定"——延续现有的防假成功策略。

**十项参数（增益/反相/延时/低通/门/压缩/EQ/插入/发送/Pre-Post）在这个模型下的工作量**：约 30 条 `ParamSpec` + 每个参数 1 个 UI 控件模板 + 真机标定。**不需要再动 `set_value` / `snapshot_state` / 路由 / 预设逻辑。**

## 五、前端模块化

现在 2098 行在 Python 字符串里，无法 lint、无法跳转。拆成三文件后仍有内嵌需求：

```
web/index.html   <link> /app.css     <script src="/app.js">
web/app.js       按域拆成若干段（仍单文件，避免构建复杂度）：
                   ├── api.js 负责的所有 fetch（统一错误处理、超时、重试）
                   ├── store.js 本地状态 + 脏标记（现有 S 对象）
                   ├── render/ 通道条 / 卡片 / 预设 / 设置
                   └── actions.js 用户操作
```

`tools/build_web.py` 把三者内联成 `assets.py`（保留现有 CSP：`unsafe-inline` + `frame-ancestors 'self'`），生产仍是"零外部请求"。

**为什么不做多文件打包（esbuild/rollup）**：本项目要能在一个 Python 文件里跑起来、要能在 macOS App 内嵌、要能离线。引入 node 构建链会让 CI 多一个失败点，收益不抵成本。**单文件 + 清晰分段**是这里的正确取舍。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 全局单例遍地（`STATE`/`BRIDGE`/`SHOW_STATE`/`SNAPSHOTS`…） | 短期**保留模块级单例**（`from x32sim.state import STATE`），不强行依赖注入；只有 `WriteSink` 与 `profile` 两处做注册制。避免"为了架构而架构"引入大量样板 |
| 循环导入 | `check_layers.py` 在 CI 里跑，出现环直接失败；`state↔bridge` 用 sink 切断，`actions↔cards` 用参数传递切断 |
| 合成单文件的执行顺序 | 禁止模块顶层副作用；`make_single.py` 按拓扑序拼并校验 `--selftest` |
| 拆分期间线上版本漂移 | 每批合并后立即重新部署在线版 + 重打 macOS 产物；协议仓 tag 只在**发布时**更新（`spec-v1.7`） |
| 测试跟着搬家导致失效 | 测试**不改逻辑**，只改启动方式（`python x32_simulator.py` 保持不变，因为入口是薄壳） |
| 时间成本 | B1/B2 各约 0.5 天，B3 约 1 天，B4/B5 各约 1 天；总计 3–4 个工作日（不含十项参数） |

## 八、和"十项参数"的衔接

做完 B0–B3（约 2 天）就可以开始十项参数，顺序建议：

1. **增益 / 反相 / 延时**（字段少、UI 简单、标定最快）→ 验证 `ParamSpec` 全链路（表 → 状态 → 地址 → 接口 → 前端 → 预设 → 卡片）。
2. **噪声门 / 压缩**（多字段，验证"整段参数组"的 UI 与预设存储）。
3. **EQ**（4 段 × 4 属性，验证嵌套参数与高频写入的合并）。
4. **插入 / 发送 / Pre-Post**（发送是 32×16=512 条，最大的一块；要单独定"状态怎么下发"）。

每加一个参数，必须同时补：
- `ParamSpec` 一条（含 `verify="真机标定"`）；
- 预设 `preset=True` 后，**回归语义**要写进规范（整段回还是逐字段回）；
- 一条回归用例（写入 → 读回 → 越界拒绝 → 预设存/回）；
- `/api/state` 的体积复测（十项全加会让 payload 从 21KB 涨到 60KB+，**必须先做 §P1-2 的差量/拆分，否则 4G 下每小时 800MB**）。

## 九、需要你拍板的三件事

1. **单文件分发是否保留**：本方案默认保留（双形态 + 合成工具）。如果你希望彻底转成"包 + pip 安装"，那 macOS App 与在线版的部署方式都要改，成本另算。
2. **重构档位**：完整做 B0–B5（3–4 天），还是只做 B0 + B1/B2（修问题 + 抽出纯函数与状态层，约 1.5 天），前端与路由暂不动？
3. **十项参数的范围**：先做「增益/反相/延时/低通/插入」这 5 项（字段少、当天可见效果），还是按文档 §8 全做（含发送 512 条，工作量约 3–5 天）？

我的建议：**B0 立刻做**（问题都在真实使用路径上，越晚修代价越大）→ **B1/B2 跟着做**（为参数扩展铺路）→ 十项参数从「增益/反相/延时」开始。B3–B5 可以边用边推。
