# 五项技术缺口：分类、方案与无真机降风险

日期：2026-10-22 · 对应代码：`X32Simulator/`（包 + 单文件双形态）
回归：`run_all_tests.py` **9/9 组通过**（params 375 项、subscribe 13 项）

## 0. 先说结论：五项不是一类问题

| # | 问题 | 分类 | 优先级 | 本轮状态 |
|---|------|------|--------|----------|
| 1 | 5 个出厂值待真台核对 | **硬件缺失**（信息不存在于公开资料） | P2 | 未核对；升级为机器可读的"未标定"标记 + 核对工具 |
| 2 | hold/keysrc/filter/insert-sel 未建模 | **逻辑缺陷**（协议有、实现没有） | P1 | 已补 18 项，端到端可读写 |
| 3 | `PUSH_CACHE` 全局、新订阅者无初始全量 | **设计缺口**（真台也没有全量，但缺协议正解） | P1 | 已实现 `/subscribe`；`/xremote` 快照做成显式开关 |
| 4 | 取点线上取值形式（索引/字符串）未验 | **硬件缺失**（回包形式未知）+ **逻辑缺陷**（字符串会静默改值） | **P0** | 已做双形式兼容 + 真机探测工具 |
| 5 | `send_level` 未按 161 档量化 | **逻辑缺陷** | P2 | 已量化（`f=k/160`） |

优先级不是按"能不能修"排的，而是按**出错后的后果**：

- **P0**：会**静默改值**（读一次真台，本地值就变了，且没有任何报错）——第 4 项属于这类。
- **P1**：功能缺失但**不会改错值**（收不到、改不了）——第 2、3 项。
- **P2**：显示/保真层面的偏差，且真台会兜底吸附——第 1、5 项。

## 1. 五个出厂默认值：硬件缺失，但可以"不假装"

### 现状核实

`ch_hpf_f`(80 Hz) / `ch_hpf_slope`(12) / `ch_ins_pos`(PRE) / `ch_gate_thr`(-40) /
`ch_gate_range`(15) 这五项，官方手册只给**范围**，社区场景文件里的是使用者设置，
不是出厂状态。所以此前只能给"合理猜测 + 注释里写需真机确认"。

问题在于：**注释不进接口**。前端、核对工具、下游三端都看不见"这是猜的"。

### 方案（已落地）

1. `ParamSpec` 增加 `unverified=True`，26 个推断值全部标注（含新增的 gate/dyn 默认值）。
2. `/api/info` 回 `calibration: {count, unverified:[kind…]}` —— 界面/工具可据此显示"未标定"。
3. `tools/verify_defaults.py` 重写：**不再是硬编码 5 条**，而是从登记表动态生成
   全部未标定项（26 条），逐条 GET、与假设值比对、打印差异百分比，支持
   `--json out.json` 落盘。

### 模拟验证方法

- 模拟器自身的默认值可以通过 `blank_row()` / `/api/state` 断言（已进回归）。
- **但这只能验证"代码与假设一致"，不能验证"假设与真台一致"** —— 这是模拟无法
  替代的部分，必须说清楚。

### 无真机降风险

| 措施 | 作用 |
|------|------|
| `unverified` 进 `/api/info` | 假设值在界面上可见，不会被当成事实引用 |
| 核对工具动态生成清单 | 借到真台时一条命令跑完 26 项，不用改代码 |
| 默认值只影响**新通道初值** | 已有场景/预设是显式快照，不会被默认值污染 |
| 回归不比对"出厂值绝对值" | 避免把猜测固化成测试基线（一改就红，逼着人把猜测当真） |

## 2. hold / keysrc / filter / insert-sel：逻辑缺陷，已补齐

### 现状核实（对照官方 OSC 表逐条核过）

| 参数 | 地址 | 类型/量程 | 备注 |
|------|------|-----------|------|
| gate/hold | `/ch/NN/gate/hold` | logf [0.02, 2000, 101] ms | |
| gate/keysrc | `/ch/NN/gate/keysrc` | **int [0..64]** | 不是 enum |
| gate/filter/{on,type,f} | 5 段地址 | bool / int[0..8] / logf[20,20000,201] | **五段**，与 EQ 同深度 |
| dyn/hold | `/ch/NN/dyn/hold` | logf [0.02, 2000, 101] ms | |
| dyn/keysrc | `/ch/NN/dyn/keysrc` | int [0..64] | 同上 |
| dyn/filter/{on,type,f} | 5 段地址 | 同上 | |
| insert/sel | `/ch/NN/insert/sel` | int [0..22] {OFF, FX1L..FX8R, AUX1..6} | 与 `insert/pos` 是两个维度 |

`keysrc` 的 65 个值按官方顺序展开：`OFF` + `In01..32` + `Aux1..6` +
`USB L/R` + `Fx1L..Fx4R` + `Bus01..16`（代码里有 `assert len == 65`）。

顺带补齐了同组缺失的 7 项：`gate/mode`、`gate/attack`、`gate/release`、
`dyn/mode`、`dyn/det`、`dyn/env`、`dyn/auto` —— 只补 hold/keysrc/filter 而不补
它们，gate/dyn 面板仍然是残的。

### 方案（已落地）

- 登记表 57 → **75 项**，ch 行 40 → **58 字段**，全部表驱动：OSC 读写、`/api/state`、
  预设范围、卡片 `set` 动作、桥接转发都自动覆盖，不需要改五处。
- 新增 `CH_DEEP_ADDR`（五段地址索引），与 EQ 的 `CH_EQ_ADDR` 分开 ——
  混用会让 `/ch/01/dyn/filter/f` 被当成"EQ 第 4 段"去查，**静默无回包**。
- 前端加"门"页签（5 个 tab），门 10 项、动态 18 项各自成组。

### 模拟验证方法

- `match_address()` 逐地址断言（含五段）；
- `set_value → get_value` 往返，对数档位用 `param_coerce` 的量化值比对
  （写 100 ms 读回 100.237 ms——101 点对数表本来就只能落在这里）；
- 越界钳制（keysrc 99→64、insert sel 99→22、filter f 99999→20000）；
- 前端控件表 vs 后端登记表逐项比对（字段名/顺序/量程/档位/默认值/精度），
  任一边漏改就红。

### 无真机降风险

- **值域不确定的项一律"取宽 + 标注"**：例如 gate/hold 上限 2000 ms 来自协议，
  但出厂值未知 → `unverified=True`，不假装。
- **keysrc 不做字符串写入**：协议明确它是 int，真台只吃整数；本地允许用名字
  *解析*（宽容读），但 `param_wire` 永远发整数。
- 默认值全部集中在 `params.py` 一行里，真机核对后改一处即可。

## 3. `PUSH_CACHE` 与"新订阅者没有初始值"：先纠正前提，再补正解

### 现状核实（这条最容易搞错）

真台的 `/xremote` **也只推变化，不推初始全量**。Mixing Station 的文档写得很直白：
"event 机制只在值变化时发数据，这也是它连接时需要一次 sync 的原因"。

所以"新订阅者收不到初始全量"**本身不是与真台不一致**。真正的不一致是：

1. `PUSH_CACHE` 是全局的，新订阅者加入时缓存已热 → 它一个包都收不到
   （而第一个订阅者因为冷缓存，反而能收到"全量"，看起来像有初始值）；
2. 我们**没有实现 `/subscribe`** —— 协议里负责"我现在就要这个值、并且按这个频率
   继续给我"的正是它。缺了它，客户端只能自己逐条 GET。

### 方案（已落地）

**协议层（正解）**

- 实现 `/subscribe ,s<地址> [,i<倍数>]`：倍数是 50 ms 的倍数，10 秒无续期自动过期；
- `due = now` → **订阅后的第一轮立刻回当前值**，这就是"初始值"的标准拿法；
- 支持通配符（`/ch/*/mix/fader` 一次订阅 32 路）；
- `/unsubscribe` 按地址退订。

**工程层（可选增强，默认关）**

- `--xremote-snapshot`：新订阅者首帧补一次全量。**默认关闭**，因为真台没有这个行为；
  打开后自研客户端联调更顺，但代码里明确标注"非真台行为，不要依赖"。
- 顺带修了一个真 bug：`PUSH_CACHE` 原来在"第一个订阅者发完"就更新，
  导致后面的订阅者算出"没变化"→ 漏发。现在改成**所有订阅者发完再更新**。
- 每个订阅者维护 `SUB_SEEN`，断开时一并清理（重连会重新对齐）。

### 模拟验证方法（`test_subscribe.py`，13 项）

```
1. 默认实例
   · 首个订阅者（冷缓存）收到 >= 60 条推子/静音
   · 后加入的订阅者收到 0 条          ← 复现缺口，证明不能依赖
   · 改一个推子 → A、B 都收到 diff
   · /subscribe 后第一轮立刻回当前值
   · rate=4 → 一秒 3..7 帧（200ms 一帧）
   · /unsubscribe 后 0 帧
   · 通配符订阅 32 路一次到位
2. --xremote-snapshot 实例
   · 后加入者收到 >= 60 条
   · 第二秒不再重发（只补一次）
3. 续期：/xremote 不会把按地址订阅顶掉
```

### 无真机降风险

- **默认行为保持与真台一致**（不补全量），避免模拟器"喂养"出一个上真台就坏的客户端；
- 需要初始值的场景走 `/subscribe` —— 这条路在真台上同样成立，不是模拟器特供；
- 回归里专门有一条"后加入者收不到"，**把这个认知固化下来**，防止以后有人
  误以为模拟器会补全量而写出依赖它的客户端。

## 4. 取点线上形式：一半硬件缺失，一半是会静默改值的真 bug

### 现状核实

协议规定 enum 既可以用 4 字节索引、也可以用名字字符串发送，真台两种都收；
但**回包**形式随固件而异（多为整数索引）。

我们原来只认整数。一旦真台回 `"POST"`：

```
param_from_wire(sp, "POST") → _finite("POST", default) → 3
```

数值解析失败 → 落回默认值 3。**表现是"读一次真台，取点就自己变回 POST"**，
没有任何报错。这已经不是"未验证"，而是**会把真台值改掉**的逻辑缺陷。

### 方案（已落地）

1. `param_from_wire`：`labels` 型参数先按名字匹配（大小写/空格容错，
   `"POST"` / `" grp "` / `"EQ->"` 都能识别），命中后返回索引；不认识再按数值解析。
   顺带覆盖 `insert/pos` 这类 bool 型（`"PRE"/"POST"`）。
2. `param_wire`：新增 `enum_wire="label"` 分支，可发名字字符串。
3. 启动开关 `--tap-wire index|label`（默认 index），`/api/info` 回 `tapWire` 如实反映。
4. 新增 `tools/probe_console.py <IP> enum`：对发送取点、插入位置、门类型、
   动态类型逐个"发索引 → 读回 → 发名字 → 读回"，直接告出这台机子回的是
   int 还是 str、是否接受名字写入。

### 模拟验证方法

两种形式都能在模拟器上跑通同一套用例，这本身就是"无真机验证"的核心：

```
默认（index）: GET /ch/01/mix/01/type → 3
--tap-wire label: GET → "POST"（字符串回包）
两种模式下: 写入 "GRP" / 4 都落到 4；写入 "POST" / 3 都落到 3
```

回归里加了 5 条单元断言（字符串→索引、大小写容错、label 模式往返、切回 index）。

### 无真机降风险

| 措施 | 作用 |
|------|------|
| 读：双形式兼容 | 真台回什么都能解析，**不会再静默改值** |
| 写：默认发索引 | 索引是协议最保守的形式，所有固件都认 |
| 探测工具 | 借到真台时一条命令出结论，不用读代码猜 |
| `/api/info.tapWire` | 现场能看出当前用的是哪种形式 |

## 5. `send_level` 161 档：量化本身不难，难在别猜错曲线

### 现状核实

`send_level` 是协议里的 `level` 类型：`[0.0…1.0(+10dB), 161]`。
第三列是**离散点数**，不是 dB 步长。161 个点 = `f = k/160`（k=0..160）等分，
再经 4 段伪对数曲线变成不均匀的 dB 步长（低区 3 dB、高区 0.25 dB）。

验证方式：`0.0625 → -60 dB` 恰好是第 10 个点（10/160），`0.25` 是第 40 个，
`0.5` 是第 80 个，`0.75` 是第 120 个 —— 全部整除，说明"等分归一值"的判断是对的。

### 方案（已落地）

- `ParamSpec` 增加通用能力 `linsteps=161`：量化 = `round(v*160)/160`。
  用"点数"而不是 `step=0.00625`，因为十进制 step 跑 160 次会漂 1e-15，
  回读比对会误判成"值变了"。
- 未标定前**不对推子做 1024 档量化**：`f=k/1023`，加进去会让默认 0.75 变成
  0.7507/0.7498，牵动所有初始值与显示，收益（< 0.001）远小于风险。已在
  规范 §5.3.1 记录，等真机确认后再开。

### 模拟验证方法

- 单元：`0.42 → 67/160 = 0.41875`、端点 0/1 不漂、`k/160` 网格逐点校验；
- 端到端：API 写 0.42 → `/api/sends` 读 0.41875 → OSC 5 段地址读同一个值 →
  卡片保存/执行 → 预设回归，全链路都按量化后的值断言；
- 真机：`tools/probe_console.py <IP> level` 扫 161 个点，输出"读回的不同值数量"
  与"与 k/160 网格的最大偏差"，不吻合就打印实测档位供标定。

### 无真机降风险

- 量化只改**本地表示**，错也只错半档（<= 0.31 dB），且真台会把任意 0..1
  吸附到最近档，不会累积；
- 量化后值更稳定（不会出现 `0.30000000000000004` 这种尾巴进 JSON/OSC）；
- 标定工具已备，真机一跑就知道要不要换成实测表。

## 6. 连带发现（超出五项，但必须说）

核第 5 项时必须先把 dB 曲线弄对，结果发现**我们一直用的曲线是错的**：

```
旧（fader_to_db）: 20*log10(f/0.75)
  0.5  → -3.5 dB    真台 -10 dB   （偏 +6.5）
  0.25 → -9.5 dB    真台 -30 dB   （偏 +20.5）

新（协议 4 段伪对数）:
  f>=0.5→40f-30 | f>=0.25→80f-50 | f>=0.0625→160f-70 | else 480f-90
  0.75→0 | 0.5→-10 | 0.25→-30 | 0.0625→-60
```

影响面：界面 dB 显示、`rel_db` 动作的移动量、DCA 级联的 dB 差、电平模拟。
**不影响下发值**（始终传 0..1 归一值），所以不是控制错误，是显示/换算错误。

已改：`params.level_db/level_from_db`（唯一一份定义）、`state.fader_to_db/db_to_fader`
转发、前端 `dbOf/dbToFader`、`共享协议规范.md` §5.3（升 v1.7）。

⚠️ **三端（iOS/Android/macOS）仍是旧式**，规范里已标"迁移状态"。
这是本轮唯一一处"模拟器比客户端更正确"的地方，同步前两端显示会不一致。

## 9. 一句话回答"无真机怎么降风险"

**把"未知"变成三样东西**：一个机器可读的标记（`unverified`）、一个能跑出答案的
工具（`verify_defaults` / `probe_console`）、一条两种假设都能活的代码路径
（枚举双形式、订阅开关）。

不把猜测写进测试基线，也不让客户端依赖模拟器的"善意"（比如自动补全量）——
后者最危险：它会让一个上真台就坏的客户端，在模拟器上一直是绿的。
