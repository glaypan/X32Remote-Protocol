# 扫码接入「两条路」设计与实现

日期：2026-10-26　规范：v1.9（§16.9）　涉及：模拟器 / 网页控制台 / iOS / Android / Windows / macOS

## 0. 结论

电脑端（Windows 桌面版、macOS Commander、命令行版）都是同一台**演出主机**：本机跑服务，
屏幕上给两张码。手机两条路都能进：

1. **浏览器路**：相机/微信扫左码 → 打开网页控制台，零安装、全功能；
2. **App 路**：iOS / Android App 内「扫码连接」扫右码（或左码）→ 自动填 IP 与端口并连上。

两条路共用同一份状态（同一个服务进程），手机上推子动，电脑页面同步。

## 1. 为什么必须是两张码

| | 浏览器码 `/qr.svg` | App 配对码 `/pair.svg` |
|---|---|---|
| 载荷 | `http://192.168.50.57:8080/` | `x32remote://pair?v=1&host=…&osc=10023&web=8080` |
| 里面的端口 | **HTTP** 端口 | **OSC/UDP** 端口（+ 网页端口） |
| 谁扫 | 手机相机 / 微信 | App 内的扫码界面 |
| 扫完 | 打开网页控制台 | 填好 IP/端口并连接 |

关键在端口语义：用户把 UDP 端口从 10023 改成 10025 之后，网页地址里的 8080
顶替不了 OSC 端口。App 若按 10023 猜，表现是**"已连接"却一条回包都没有** ——
这类"安静的错误"最费现场时间（见 §13.1 的假成功原则：宁可不连，也不要假装连上）。

同时 App 的解析器**接受浏览器码**：扫左码时按默认 10023 处理。
现场最常见的动作就是拿 App 去扫屏幕上那张码，不该逼人分辨。

## 2. 载荷与接口

```
x32remote://pair?v=1&host=192.168.50.57&osc=10023&web=8080
```

| 字段 | 必填 | 规则 |
|---|---|---|
| `v` | 是 | 载荷版本；当前 1 |
| `host` | 是 | 局域网地址；`127.*` / `localhost` / `0.0.0.0` **非法** |
| `osc` | 是 | 1–65535，默认 10023 |
| `web` | 否 | 网页端口，自动增益/推子等 HTTP 接口要用 |

整串 58 字节 → 二维码 v4（33×33），屏幕上 118 px 仍有 3.6 px/模块，够扫。

接口：

- `GET /pair.svg?h=&o=&w=` —— 缺省取服务端当前 `LAN_IP/UDP_PORT/WEB_PORT`；
  非法主机或端口 → 400；白底、4 模块静区、`Cache-Control: no-store`
- `GET /api/info` 新增 `pairCode`（原文）与 `pairQr`（`"/pair.svg"`）；
  探测不到局域网（只剩回环）时 `pairCode` 为空串，前端据此隐藏右码并说明原因
- 终端启动横幅在网页二维码之后多打一行 `App 扫码配对码: …`，便于复制

## 3. 三端实现

| 端 | 文件 | 说明 |
|---|---|---|
| 模拟器 | `X32Simulator/x32sim/pair.py` | 载荷拼装 / 解析 / 主机与端口校验 |
| 模拟器 | `x32sim/httpapi.py` | `/pair.svg`、`/api/info` 字段 |
| 网页 | `web/index.html` + `app.css` + `app.js` | 双码并排、复制配对码、无地址时隐藏 |
| iOS | `Sources/X32RemoteCore/Pair/PairCode.swift` | 解析（与 Python 同规则） |
| iOS | `App/Views/QRScannerView.swift` | AVFoundation 取景；识别一次即停 |
| iOS | `App/Views/SettingsView.swift` | 「快速连接 → 扫码连接」→ 填 IP/端口并连 |
| Android | `core/PairCode.kt` | 解析（同规则） |
| Android | `MainActivity.kt` | 菜单首项「扫码连接」→ ZXing `ScanContract` |

iOS 用系统 AVFoundation 而不是第三方库；Android 用 `zxing-android-embedded`
（`ScanContract` + 取景界面现成，少两百行且各家对焦行为已被它抹平）。

## 4. 解析规则（三端必须逐条一致）

接受三类载荷：

1. `x32remote://pair?v=1&host=…&osc=…&web=…`
2. `http(s)://<host>[:port]/` —— 网页码，`osc = 10023`，`web = URL 端口`
3. `<host>[:port]` —— 其它工具生成/手输

拒绝：`javascript:` / `ftp://` 等伪协议、端口越界（0、>65535）、IPv4 段 >255、
回环地址、长度 >200、空串。识别失败时**不改动**当前 IP/端口 —— 半截地址比不连更困惑。

## 7. 已知限制

- **服务端无鉴权**：同网段任何人扫到都能控制（与真台 OSC 同一信任模型）；演出网络建议独立 SSID。
- **相机权限**：拒绝后只能手填；两端都给了明确提示与「去设置」。
- **Deep link 未接**：`x32remote://` 目前只被 App 内扫码识别。用系统相机扫 App 码不会自动拉起
  App（iOS 需要 `CFBundleURLTypes`，Android 需要 intent-filter）。不影响两条路可用性。
- **多网卡/VPN**：IP 靠默认路由探测，取错时两张码都指向不可达地址；设置页有「复制地址」可改。
- **必须在同一可达网络**：跨网段/AP 隔离/防火墙拦截都会表现为"扫了打不开"。
