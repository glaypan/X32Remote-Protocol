# X32 卡片自动化 · 优化方案设计文档

> 状态：P0 全部 + E5 冲突策略(2026-09-24,按用户要求「只停干预通道」) + P1(A1/A3 时间轴调度器、at 并行、C1 卡片链、B3 rel_db 相对动作、E3 雏形/xremote 续期) 已实施；剩余 P2: 定时触发 C2、循环 C3、状态高亮 D2、防误触 D3、回执 D4、导入导出 D5
> 对象：`X32Simulator/x32_simulator.py` 的卡片执行引擎
> 日期：2026-09-23

---

## 一、目标

让「卡片」从**动作清单**升级为**自动化编排工具**，能表达现场演出真实需要的时序与目标逻辑：

- 能表达「静音 A → 等 3 秒 → 渐入 B」这类有节奏的多步流程
- 能表达「通道 1 渐出的同时通道 2 渐入」这类并行关系
- 目标可以是任意通道集合，并且用真台的通道名称而不是编号来编排
- 执行出错时能一键回到执行前

---

## 二、现状盘点

### 2.1 已具备能力

| 项 | 现状 |
|---|---|
| 动作类型 | 10 种：`mute` / `mute_bus` / `scene` / `unmute_all` / `fade_all` / `fade_odd_even` / `fade_ch` / `fade_bus` / `fade_from` / `fade_from_bus` |
| 覆盖对象 | 32 输入通道 + 6 Aux In + 2 USB 返回 + 8 FX 返回 + 16 Bus + 6 Matrix + 8 DCA + 主输出（共 79 只推子） |
| 曲线 | `linear` / `ease_out` / `ease_in` / `smooth` |
| 中断 | 全局 `SHOW_STOP`，可中途停止 |
| 进度 | `SHOW_STATE["progress"]`，按步数累加 |
| 持久化 | 卡片与按键写入 `user_config.json`，重启不丢 |

### 2.2 关键实现位置

| 位置 | 作用 |
|---|---|
| `run_show()` L783 | 卡片执行入口，`worker()` 线程 |
| `timed_fade()` L818 | 渐变执行：内部 `sleep` 步进，**阻塞式** |
| `_clean_action()` L937 | 提交动作的白名单校验与数值钳制 |
| `save_snapshot()` L542 / `recall_snapshot()` L558 | 快照保存与回归 |
| `clear_console()` L722 | 空台子 |
| `CURVES` L934 | 曲线白名单 |

### 2.3 三个结构性短板

1. **时间是隐式的**
   `run_show` 是 `for act in card["actions"]` 顺序循环，每条渐变在 `timed_fade` 里同步 `sleep` 到结束。结果是：
   - 没有「等待 N 秒」这个动作，拼不出带间隔的流程
   - 无法在中途插入别的动作，长渐变期间主线程被独占
   - 「全体同时动」是靠 `fade_all` 硬编码的特例，无法自定义并行组合

2. **目标粒度断层**
   目标只有「单个通道 / 单个 Bus / 全体 / 奇偶」四种写法，中间的「任意几个」不存在。且只能用数字编号，`_clean_action` 也只接受 `ch: int`。

3. **执行不可逆**
   `run_show` 执行前不保存状态，跑错了只能手动推回来。虽有快照功能，但需要用户手动先存。

## 三、优化项详述

### 维度 A｜时间：补上等待与并行

#### A1. 新增「等待 N 秒」动作

- **动作**：`{"kind": "wait", "duration": 3.0}`
- **语义**：占用时间轴 N 秒，不改变任何推子
- **改动点**：`_clean_action` 白名单加 `wait`；`run_show` 加分支（当前模型下直接 `sleep(duration)`，接入调度器后成为一条空动作）
- **价值**：高。这是"多步编排"最基础的一块，没有它就无法表达节奏

#### A2. 动作分组（组内并发 / 组间串行）

- **数据**：`{"kind": "group", "parallel": [act, act, ...], "duration": null}`
- **语义**：组内所有动作同时开始；组的总时长取组内最长者；组与组之间顺序执行
- **替代方案**：不给分组，直接给每条动作加 `at`（起始时间偏移），由调度器按时间轴统一驱动 —— **推荐后者**，表达力更强且模型更简单
- **价值**：高。能自定义任意并行组合，不再依赖 `fade_all` 这种特例

#### A3. 时间轴调度器（核心重构）

把阻塞式 `for` 循环换成统一 tick 推进：

```
tick = 0.05s
每条动作挂到时间轴上: { act, start, end }
循环体:
    t += tick
    对每条处于 [start, end] 的动作:
        瞬时动作 -> 在 t == start 时执行一次
        渐变动作 -> 计算 ratio 并 set_value
        等待动作 -> 不做事
    更新进度 = t / 总时长
```

- **收益**：并行、等待、中途插队、停止时立即冻结当前值，全部天然成立
- **风险**：这是对执行核心的改动，回归面大。**建议保留旧执行路径，用参数开关切换**，新引擎先并行验证
- **连带改动**：进度计算从"步数累加"改为"总时长比"，`total` 的算法要重写

### 维度 B｜目标：从编号到语义

#### B1. 多目标选择

- **数据**：`"targets": {"group": "ch", "ids": [1, 3, 5, 7]}`，兼容旧的单值写法
- **UI**：动作构建器里把「通道号」数字框换成可多选的通道选择器
- **改动点**：`_clean_action` 的 `ch: int` 改为接受数组并逐个钳制到 1..32、去重；`run_show` 的单一 `timed_fade([...])` 改为展开为多条 target
- **价值**：高

#### B2. 接入 X32 通道名称

- **协议**：真台支持 `/ch/01/config/name` 读写，Bus / DCA 同理
- **模拟器侧**：`MixerState` 的每路增加 `name` 字段 + 一份默认名称表；`/api/state` 输出名称
- **UI**：所有下拉与卡片简介显示「03 · 人声」而不是「通道 03」
- **额外收益**：根治「简介与动作描述对不上」这类观感问题 —— 卡片上直接写「音乐 从 0 渐强到 90%」，用户一眼能核对
- **桥接模式**：连接真台时先拉一次名称表并缓存
- **价值**：高（可读性提升最明显，实现成本低）

#### B3. 相对动作（+3dB / -3dB）

- **数据**：`{"kind": "fade", "rel": true, "delta_db": 3.0}`
- **需要的前提**：X32 推子位置（0..1 float）与 dB 是**非线性**关系，必须引入官方推子曲线查表才能让「+3dB」在低端和高端手感一致。这是本项的主要成本，建议单独做一张曲线表并加单元测试
- **价值**：中高。现场微调很常用

#### B4. 记录当前值（Learn）

- **数据**：`"from": "current"` 或 `"to": {"learn": true}`
- **语义**：运行时取"此刻推子位置"作为起点或终点
- **价值**：中。适合「从当前位置渐变到 X」这种不想写死起点的场景

### 维度 C｜流程：卡片之间连起来

#### C1. 卡片链 / 歌单

- **数据**：卡片增加可选 `"next": "<cardId>"`；或独立结构 `{"id": "...", "name": "演出流程", "steps": ["<cardId>", ...]}`
- **UI**：卡片页显示「上一首 / 下一首」，当前位置高亮
- **语义**：一张卡跑完自动接下一张；也可手动步进
- **价值**：高。这是"演出流程"级的用法，比单张卡更接近实际工作流

#### C2. 定时触发

- **语义**：指定时刻自动执行某张卡（如开场曲 20:00 执行）
- **改动点**：服务端一个轮询线程 + 卡片上的 `schedule` 字段
- **价值**：中。实现简单，偶发但很实用

#### C3. 循环 / 重复

- **语义**：卡片每 N 秒重复，或重复 M 次（配合 All Live 那类动效）
- **价值**：中低。偏玩具向

#### C4. 外部触发（需先实测确认）

- **设想**：台子上的用户键或 MIDI 触发我们的卡片
- **注意**：**X32 的 OSC 实现主要是服务端角色**（监听 + 响应查询 + 订阅后推送电平），是否支持「按键主动发出任意 OSC」在官方文档里没有明确承诺。因此这项不能直接按"按键发 OSC"设计
- **可行路径**（按可靠性排序）：
  1. 我们监听 **MIDI**：X32 的 Assign 键可发 MIDI 消息，走 USB 或 5-pin DIN，服务端加一个 MIDI 监听器
  2. 由另一台设备/软件（如 Mixing Station、Bitfocus Companion）发 OSC 到我们的服务端
  3. 移动端 NFC / 蓝牙按键 → 服务端 HTTP 接口
- **结论**：这一项**建议先实测**再决定实现方式，不要按未验证的假设开工

### 维度 D｜安全与回馈

#### D1. 一键撤销

- **机制**：`run_show` 执行前自动调用 `save_snapshot()`，标记为 `auto`（不进用户的预设列表，单独一个栈，深度 5）
- **UI**：卡片页顶部「撤销上一次」，点击后按 3 秒回归
- **价值**：高。现场救命功能，且能复用现成的快照回归代码
- **注意**：需要在卡片页明确区分「用户的预设快照」和「系统自动快照」，避免污染

#### D2. 状态感知高亮

- **语义**：卡片记录目标状态，与实时状态比对，若台面已处于该状态则卡片显示为「已就绪」
- **价值**：中。避免重复执行造成重复叠加

#### D3. 防误触

- **语义**：卡片标记 `danger: true` 时，需长按 800ms 或滑动确认才执行（如全体静音、拉底）
- **价值**：中。手机单手持机时很需要

#### D4. 执行回执

- **语义**：每步的实际耗时与结果写进日志区，卡片可展开查看
- **价值**：中低

#### D5. 配置导入导出

- **接口**：`GET /api/config/export` 下载 JSON；`POST /api/config/import` 导入
- **价值**：中。备份与分享给同事

### 维度 E｜参数与信息同步（卡片 ↔ 调音台）

回答「卡片能否同步调音台参数和信息」：能，但分三个层次，成本差异很大。

#### E1. 卡片显示实时参数（读方向）

- **现状**：服务端已每 250ms 聚合一次完整状态（79 只推子位置、静音、电平），前端已在轮询。**数据早已送到前端，只是卡片上没有展示**
- **方案**：卡片副标题显示实时值，例如
  ```
  音乐 · 通道 15        当前 32% → 目标 90%
  耳返 · Bus 15         当前 75%
  ```
- **成本**：低（纯前端）

#### E2. 用实时值当参数

- **Learn 起点**：`"from": "current"`，执行瞬间取当前值，不写死（依赖 B4）
- **条件执行**：如「只有当通道 5 已静音时才渐入通道 6」——执行前读状态判断
- **状态高亮**：台面已处于该卡目标状态时显示「已就绪」，避免重复执行（同 D2）
- **成本**：低

#### E3. 台面改动反向进卡片（真同步的关键）

- **问题**：X32 不会主动推送参数变化，**只在客户端订阅后才推**。需要定期发送 `/xremote` 续订（约每 10 秒一次），否则台面上其他人手动推的推子，我们完全感知不到；电平表数据则需要 `/subscribe`
- **现状**：模拟器是自研服务端，状态自己维护，天然成立；**接真台必须补这一步**
- **方案**：加一个保活续订线程 + 入站消息解析，把台面改动写回本地状态，卡片即时刷新
- **成本**：中（属于桥接模式的一部分）

#### E4. 信息类读取（不只是参数）

| 信息 | 协议 | 用途 |
|---|---|---|
| 通道名称 | `/ch/01/config/name` | 卡片用名称而非编号编排（与 B2 同一件事） |
| 通道颜色 | `/ch/01/config/color` | 卡片配色与台面保持一致 |
| DCA 成员 | DCA 相关地址 | 卡片按编组选目标 |
| 当前场景号 / 场景名 | 场景相关地址（**具体地址需核对官方 OSC 文档后再实现**） | 卡片显示「当前第 N 场」 |
| 台子型号 / 固件 / IP | `/xinfo` | 设置页展示设备信息，确认连对了台子 |

#### E5. 冲突策略（双向同步的核心难点）

- **场景**：卡片正在执行 5 秒渐变，同时有人在台面上手动推同一路推子
- **可选策略**：
  1. 最后写入者胜 —— 实现最简单，但会出现推子互相打架、数值抖动
  2. **卡片执行期间锁定目标通道（推荐）** —— 符合电动推子的物理直觉
  3. 检测到手动干预即中止该动作并提示
- **结论**：必须明确选定一种，否则双向同步会表现为"推子抽搐"

#### E6. 前提条件

当前同步的对象是内置虚拟调音台（状态由服务端自行维护）。要与**真台**同步，需先实现**桥接模式**：网页操作 → 转成 OSC 发给真台 IP，同时把真台状态回读。E3 与 E4 本质上都属于桥接模式的组成部分。

#### E7. 附带收益

卡片从「写死的描述」变为「实时读取的真实参数」，用户在台面上改动后卡片立即反映，**从机制上消除了「简介与动作描述不一致」这类问题的可能**。

## 四、数据模型演进

### 4.1 建议的动作结构（v2）

```json
{
  "kind": "fade",
  "targets": {"group": "ch", "ids": [1, 3, 5]},
  "from": "current",
  "to": 0.8,
  "rel": false,
  "delta_db": null,
  "duration": 3.0,
  "curve": "linear",
  "at": 2.0
}
```

- `at` —— 在卡片时间轴上的起始偏移（秒），缺省则接在上一条之后
- `targets` —— 统一的目标描述；旧的 `ch` / `bus` 单值写法在加载时自动转换
- `from` —— 数值或 `"current"`

### 4.2 兼容性策略

1. `user_config.json` 增加 `version` 字段
2. 启动加载时做一次迁移：旧 `fades` 机制（已处理过一次）、旧单值 `ch` / `bus` 写法、无 `at` 的动作，统一转成 v2
3. 迁移后回写文件；迁移过程写日志，便于排查
4. 网页提交仍走 `_clean_action` 白名单，非法类型丢弃、数值钳制

## 六、风险清单

| 风险 | 说明 | 应对 |
|---|---|---|
| 执行核心重构 | A3 触及 `run_show` 主逻辑，回归面大 | 保留旧路径 + 开关切换，新增与旧路径做结果对比测试 |
| dB 曲线 | 位置与 dB 非线性，未查表时「+3dB」手感不一致 | 引入官方曲线表 + 单元测试覆盖若干锚点 |
| 配置迁移 | 二次迁移可能吃掉用户已有卡片 | 迁移前自动备份 `user_config.json.bak`，迁移后校验卡片数量 |
| 后台线程异常静默 | 之前踩过（`timed_fade` 元组解包 bug 导致线程静默死亡，接口仍返回 200） | 调度器循环整体包 `try/except` 并写日志；测试必须验证**效果**而不只看接口返回 |
| 协议能力假设 | C4 外部触发依赖对 X32 能力的假设 | 先实测再设计，不按假设开工 |

## 七、验收标准（每批实施后按此验证）

1. Python 编译通过 + 页面内联 JS 用 `node --check` 校验通过
2. 端到端：通过 HTTP 接口真实提交卡片 → 运行 → 断言推子**实际值**（含中途采样与终态）
3. 重启服务后配置与卡片完好，通道/按键/卡片数量符合预期
4. 旧卡片（含内置 8 张）全部可正常运行，无回归
5. 非法输入（越界编号、未知动作、超长数组）被正确钳制或丢弃，不产生异常
