# 手机控台方案 A / B 对比分析

> 状态：分析文档（未改动任何代码）
> 对象：X32Simulator/x32_simulator.py 的卡片引擎与桥接模块
> 日期：2026-09-25

---

## 0. 先立一条硬约束，所有结论都从它推导

**浏览器永远不能直接发 UDP。** 网页只有 HTTP/WebSocket/WebRTC，无法向调音台发 OSC 包。

由此得到本项目的总原则：

> **卡片引擎跑在哪台设备上，自动化功能就只能在哪台设备上存在。**

- 卡片引擎在电脑 → 必须有一台电脑在链路里（= 方案 B）
- 想在手机上跑卡片 → 手机里必须有一个**能发 UDP 的原生进程**（原生 App，或一个能在手机上跑的服务）

方案 A 之所以"轻"，是因为它把 UDP 发给了 App 开发者；代价就是功能集由对方决定，我们插不进去。

---

## 1. 方案 A 能否实现方案 B 的演出卡片？

结论：**分四条子路径，全部都无法完整复刻；最好的一条能覆盖约六成，且要另起一套配置。**

### A1 · 用调音台自带的 场景 / 片段 / 线索（Scenes / Snippets / Cues），手机 App 只负责触发

| 项 | 评估 |
|----|------|
| 可行性 | 高。X32 自带 100 场景 + 100 片段 + 500 线索槽，OSC/MIDI 都能触发（PC CH01 触发场景、CH02 触发片段、CH03-06 触发线索） |
| 难点 | **台子没有渐变时间**——片段和场景都是"按下瞬间到位"，官方社区公认的痛点（用户想给快照加 6 秒交叉淡变，台子做不到）。我们卡片里最核心的 `fade_ch / fade_from / rel_db / 并行 at` 全部无法表达 |
| 优点 | 不依赖任何外部软件；断网也能用；配置存在台子里，换手机/换电脑都在 |
| 缺点 | 只有"瞬时状态"这一半能力；250 个槽位要手工在台子面板上搭；改一张卡片要重新进台子菜单 |
| 覆盖度 | 瞬时类（静音/取消静音/整场切换）✓；渐变、相对 dB、并行、等待、撤销、冲突保护 ✗ |

### A2 · 用 Mixing Station 自带的动作列表（Actions + Fade time）复刻卡片

| 项 | 评估 |
|----|------|
| 可行性 | 中。Mixing Station 确有"一个按钮绑一串动作、按顺序执行、动作可带 Fade time"的机制，能做出"取消静音 → 渐强"这类两步卡片 |
| 难点 | 官方 issue 已明确承认**渐变不会阻塞后续动作**（渐变动一下就立刻跑下一条），且修它需要重写整个动作系统（2023 年提出，至今仍在 wishlist）；没有显式"等待 N 秒"动作；没有条件判断；一个按钮只能绑一个动作列表，做不了卡片链 |
| 优点 | 手机装个 App 就有；界面成熟稳定；控制台 UI 体验好 |
| 缺点 | 无撤销、无冲突保护（真台有人动推子我们察觉不到）、无定时触发、无状态高亮；**每台手机各配一份**，我们的网页卡片配置无法导入进去，等于同一套演出逻辑要维护两份 |
| 覆盖度 | 瞬时 + 单步渐变 ~60%；卡片链、撤销、冲突、定时、高亮 ✗ |

### A3 · 自研原生 App（Android Kotlin / iOS Swift）内置 OSC + 卡片引擎

| 项 | 评估 |
|----|------|
| 可行性 | 技术完全可行，功能可以对等甚至更好 |
| 难点 | 工作量最大：双平台原生 UDP + 卡片引擎 + 编辑 UI + 持久化，保守估计人月级；后续每次改卡片格式要发版；iOS 上架/签名又是一道坎 |
| 优点 | 体验最好，无需电脑，功能 100% 对等 |
| 缺点 | 成本与收益严重失衡——我们已经有能跑通的引擎和界面，只为"去掉电脑"重写一遍不划算 |
| 覆盖度 | 100% |

### A4 · 手机本地跑现有的 Python 服务（Termux / a-Shell）+ 浏览器访问 localhost

| 项 | 评估 |
|----|------|
| 可行性 | **最高**。`x32_simulator.py` 是纯标准库单文件，不依赖任何第三方包，Android 的 Termux 装个 python 就能跑；手机浏览器打开 `127.0.0.1:28080`，功能与电脑端完全一致（含卡片、撤销、冲突、定时） |
| 难点 | ① Termux 对普通用户有门槛（要敲命令）② Android 会杀后台，必须 `termux-wake-lock` + 关电池优化 ③ iOS 侧 a-Shell/iSH 更折腾，不建议 ④ 演出中手机来电、切 App、锁屏都可能中断 UDP |
| 优点 | 代码几乎零改动（一份启动脚本 + 说明）；配置/卡片与电脑端完全通用，导出导入即同步；换手机不用重配 App |
| 缺点 | 运行环境不稳定因素多；手机当服务端耗电明显；不适合当"演出主控" |
| 覆盖度 | 100% |

**A 路线的共同结论**：真正"手机直控"的官方 App 路线（A1/A2）只能覆盖约一半的卡片能力，且配置会分裂成两套；想 100% 对等，必须让手机自己能跑引擎（A3 自研 / A4 塞现有服务）。

## 2. 方案 B 能否做到"同局域网即可、零配置"？

结论：**能做到接近零配置，且改动很小；真正的"无电脑"就等于 A4。**

当前状况值得澄清一句：**手机端本来就已经是零配置**——不装任何 App，打开网址即用。目前唯一要填参数的地方是"桥接目标真台 IP"，而且是在网页设置页填（命令行参数只是备用入口）。所以要做的是把"填 IP"这一步也省掉。

### B1 · 自动发现真台 + 一键连接（推荐做）

| 项 | 评估 |
|----|------|
| 实现 | 网页点「🔍 扫描」→ 后端向子网广播地址发 `/xinfo`（端口 10023）→ 收集回包得到 `IP / 型号 / 固件` → 列表展示，点一下就连上 |
| 为什么可行 | `/xinfo` 是 X32 官方协议自带查询，X32-Edit 就是靠它发现台子的；**我们的模拟器也已经实现了 `/xinfo` 应答**，所以这条链路在双实例环境下立刻能测 |
| 改动量 | 后端新增 `/api/scan`（约 40 行，含广播发送 + 收包窗口 + 结果去重）；前端设置页加扫描列表与一键连接（约 30 行）。共 70-80 行，不动现有架构 |
| 附加 | 记住上次连接的台子，下次启动自动重连；电脑端可做成开机自启，实际体验就是"手机打开网址 → 已连上" |
| 风险 | 少数路由器禁止定向广播，可退化为"扫描本机网段逐个单播"，或手工填 IP 兜底 |

### B2 · 彻底不用电脑（= 手机跑服务）

即 A4。这就等于把方案 B 整个搬到手机上，见上一节评估。

### B3 · 电脑常驻、手机零安装（现状 + B1）

电脑放在机柜里跑服务（建议有线网口），手机只当控制端。演出可靠性最高：手机没电/来电/锁屏都不影响自动化执行，因为引擎在电脑上。

## 4. 推荐方案与理由

### 推荐：主线走 B1，A 只作应急备胎；若要"真无电脑"，用 A4 而不是 A1/A2/A3

**理由：**

1. **卡片能力是这套系统的核心价值，而它只能在 B 路线完整保留。** A1/A2 能覆盖的都是"瞬时状态"类，恰好是我们已经用得很顺的那一半；渐变、撤销、冲突保护、定时这些真正体现价值的，官方 App 一个都没有。
2. **B1 的改动成本极低（70-80 行），收益是"配置归零"。** 我们要付出的只是实现一个子网扫描，而手机端本来就不用装东西——这条路把方案 B 唯一的短板（要填 IP）补掉了。
3. **可靠性上，电脑当服务端远胜手机当服务端。** 演出场景最怕的是控制链路中断：电脑可以插网线、常驻供电、开机自启；手机则面临来电、锁屏、后台被杀、电量告急。让引擎待在电脑上，手机只做遥控器，是风险最低的结构。
4. **A4 作为"无电脑"的正解，成本比 A3 低两个数量级**，且卡片/命名/预设与电脑端是同一份 json，随时可迁移。若你确实有"只带手机去现场"的需求，优先做 A4（一份 Termux 启动脚本 + 说明文档即可）。
5. **A3（自研 App）不建议**，除非这套东西未来要产品化卖给别人；否则就是为去掉一台电脑重写整个前端与引擎。
6. **A1 有一个值得单独采纳的亮点**：把"瞬时状态类卡片"落成台子里的场景/片段，可以让演出在**完全没有外部设备**时也有一条保底路径（台子面板直接按，或台子自身 MIDI 触发）。这不是替代方案，而是给关键卡片加一层"硬件兜底"，值得作为后续可选功能。

### 落地清单（按优先级）

| 优先级 | 事项 | 具体改动 |
|--------|------|----------|
| P0 | 真台自动发现 | 后端 `/api/scan`：向子网广播发 `/xinfo`，收 1.5 秒回包，去重后返回 `[{ip, name, model}]`；广播失败时退化为网段单播扫描 |
| P0 | 一键连接 + 记忆 | 设置页加「🔍 扫描调音台」按钮与结果列表；点选即调 `/api/bridge`；上次地址写入配置文件，启动时自动重连 |
| P1 | 电脑端常驻 | 提供 Windows 开机自启（计划任务）或服务化说明，做到"手机打开网址就已经连上台子" |
| P2 | 手机跑服务（无电脑场景） | Android 一键脚本：安装 Termux → 拉取 `x32_simulator.py` → `termux-wake-lock` → 后台启动；附"关电池优化"图解说明；iOS 不做，改用方案 A 官方 App 兜底 |
| P3（可选） | 关键卡片落成台子场景 | 卡片编辑器加「导出为调音台场景/片段」提示（给出该动作对应的场景内容清单，人工在台子上建），用于断网保底 |

## 5. 一句话结论

**"手机直连"省掉的是一台电脑，代价是丢掉一半的卡片能力并多维护一套配置；"电脑桥接"多要一台机器，换来完整能力与更高可靠性。** 因此推荐：保留 B 路线为主线，用自动发现把配置成本降到"点一下"；真要脱机，走 A4（手机本地跑现有服务）而不是让官方 App 去复刻卡片。

## 附录 A · A3（自研原生 App + OSC）详评，重点回答"iOS 行不行"

**总评：技术上完全可行，iOS 上尤其可行——难度不在"能不能发 OSC"，而在引擎移植与分发签名。**

### A3-1 iOS 可行性拆解

| 关注点 | 结论 | 说明 |
|--------|------|------|
| UDP/OSC 直发 | ✅ 完全没问题 | `Network.framework` 的 `NWConnection(host:port:using:.udp)` 原生支持；也可用 BSD socket 或第三方 CocoaAsyncSocket。X32 的 OSC 是明文 UDP，无 TLS、无鉴权，手机连同一 Wi-Fi 即可直控 |
| 系统权限 | ⚠️ 需声明一条 | iOS 14+ 访问局域网要在 Info.plist 写 `NSLocalNetworkUsageDescription`（首次连接会弹"允许访问本地网络"），不是障碍，但必须做 |
| 现有资产 | ✅ 已有一半 | 本项目已有 `X32Remote-ios`（SwiftUI 外壳 + `X32RemoteCore`：Osc 编解码 / Model / Show 引擎，92 个单测）→ iOS 分支不是从零，等于"接引擎 + 补卡片 UI" |
| **后台运行** | ❌ **最大限制** | iOS 切后台约 30 秒即挂起网络活动（除音频/定位等特例）。**这决定 iOS App 只能当前台遥控器，不能当常驻服务**——演出中锁屏或切 App 就可能断链。想续命只能用后台音频等模式，审核有风险且耗电 |
| 分发安装 | ⚠️ 自用可行 | 免费 Apple ID 真机直装（签名 7 天需重签）；付费开发者账号 $99/年 → Ad Hoc 100 台设备、TestFlight 内测，自用绰绰有余 |
| 界面工作量 | 中 | 卡片/控制键/推子/命名等页面需用 SwiftUI 重做（网页版 UI 不能直接复用） |

### A3-2 Android 侧（对比参考）

- 原生 `DatagramSocket` 发 UDP 更简单；后台限制宽松（**前台服务 + 常驻通知**可长时间运行）→ Android 反而比 iOS 更适合"手机自己当服务端"
- 分发无门槛（直接装 APK），无需开发者账号

### A3-3 真要做的架构建议

1. **抽纯逻辑层**：把 OSC 编解码 + 卡片引擎（时间轴调度、冲突策略、撤销、相对 dB）做成不依赖 UI/平台的模块，UI 与平台外壳分离
2. **卡片定义零改动**：直接读写现有 `user_config.json` 的结构 → 与网页端同一份配置，导出导入互通
3. **防逻辑漂移（关键）**：把现有 `selftest.py / test_conflict.py / test_new_features.py / test_bridge_p2.py` 固化为**黄金验收用例**，Swift/Kotlin 实现必须跑通同一批用例。否则 Python 与 App 两份引擎必然越走越偏
4. **成本量级**：iOS 补引擎 + 卡片编辑 UI ≈ 数周；Android 从零 ≈ 更大；两端共用黄金用例可显著压住回归风险

### A3-4 什么时候才值得做

| 场景 | 是否推荐 A3 |
|------|-------------|
| 只想去掉现场那台电脑 | ❌ 不值——A4（手机跑现有服务）成本低两个数量级，功能一样完整 |
| 想长期产品化 / 给别人用 / 上架分发 | ✅ 值得——那时"装个 App 就能用"才是门槛最低的交付形态 |
| iOS 用户想在演出中依赖手机自动化 | ❌ 不建议——后台挂起机制决定它当不了可靠的服务端 |

**一句话**：iOS 可以做，而且项目已有骨架；但它是"产品化"路线，不是"去电脑化"路线。

## 附录 B · B3 落地记录（2026-09-25 已实施并验证）

**B3 = 电脑常驻服务 + 手机零安装**，已把"填 IP"这一步彻底去掉。

### B-1 新增能力

| 能力 | 实现 |
|------|------|
| 调音台自动发现 | 后端 `/api/scan`：向 `255.255.255.255` 及各网卡定向广播（如 `192.168.50.255`）发 `/xinfo`（X32 官方发现指令，X32-Edit 同款）→ 收 1.4 秒回包；**广播被拦时自动退化为按 /24 逐地址单播扫一遍**（Windows 下已处理 ICMP 端口不可达导致的 UDP 假连接重置） |
| 多网卡去重 | 同一台设备会从本机每张网卡各回一个包（本机有 ZeroTier/vEthernet 时曾一次列出 4 条）→ 按"设备 + 端口 + 型号"归并，优先保留与我们在同一网段的地址，其余地址列在 `also` 里 |
| 结果识别 | 排除自身实例（同 IP + 同 OSC 端口）；本机其他实例标注「本机模拟器」 |
| 一键连接 | 设置页新增「🔍 扫描局域网调音台」，结果以芯片形式列出，点一下即连 |
| 记住地址 + 自动重连 | 连接成功后把 `IP:端口` 写入 `user_config.json` 的 `bridgeTarget`；服务启动 3 秒后自动重连（手机打开网页时就已经连上台子）。**主动点「断开」会清空记忆**，不会莫名回连 |
| 连接健康提示 | 真台 20 秒无回包 → 每 30 秒日志提示一次"检查地址/网线/是否同网段"，不再静默 |
| 电脑端常驻 | 新增 `start_service.bat`（最小化窗口后台启动服务）、`install_autostart.bat`（注册登录时自动启动的计划任务）、`remove_autostart.bat`（取消）。脚本内容纯 ASCII、路径用 `%~dp0`，中文路径下也不会乱码 |
| 回归助手 | 新增 `wait_ready.py`：等待 OSC + Web 双就绪再跑测试（避免固定 sleep 造成的假失败） |

### B-2 顺手修掉的启动慢问题

`http.server.HTTPServer.server_bind()` 默认会做一次 `socket.getfqdn()` **反向 DNS 解析**——本机装了 ZeroTier/多张虚拟网卡时这一步会卡十几秒，期间 OSC 主循环还没开始（表现为"服务刚起时连不上"），这就是此前"Web 启动约 12 秒"的真正原因。已用自定义 `WebServer` 跳过该解析，启动从十几秒降到 1 秒级。

| `selftest.py` | 14/14 |
